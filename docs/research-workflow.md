# 가벼운 연구 절차와 판정 규칙

갱신: 2026-10-04 · [제품 정의](product-direction.md)를 따릅니다.

## 1. 연구 루프

프로젝트 이해 → 지침 작성 → 타당성 점검 → 유효한 기준 확보 → 가설·수정·코드 커밋 → 실행 → 비교·결과 기록 커밋 → 다음 실험 또는 종료

기존 코딩 에이전트가 [program.md](../templates/program.md)를 읽고 수행하는 절차입니다. 별도 그래프 엔진을 필수로 두지 않습니다. 사용자가 이미 맡긴 작업 범위에서는 매 실험마다 재확인하지 않습니다.

구현할 명령과 저장 구조는 [v1 계약](cli-and-file-contract.md)을 따릅니다. 이 문서의 실험 상태 표시는 설명용이며, v1 JSON에서는 execution.status, decision.validity, decision.status를 분리해 저장합니다. CLI는 기록·비교를 담당하고 실제 학습·코드 되돌리기를 수행하지 않습니다.

| 단계 | 수행과 결과 |
|---|---|
| 이해 | 목표·데이터·코드·명령·기존 결과를 읽고 근거 위치를 연결. 필수 정보가 없으면 해당 작업만 대기 |
| 지침 | 변경 범위, 비교 조건, 실행 예산, 중단 조건을 프로젝트별로 기록 |
| 점검 | 아래 점검 항목을 적용. 확인된 비교 무효 사유는 먼저 수정하고, 의심은 필요한 관측으로 확인 |
| 기준 | 기존 명령으로 실행하고 유효한 로컬 기준 점수·로그·코드 상태를 저장 |
| 실험 | 가설과 예상 효과를 적고 해석 가능한 범위로 코드/설정을 변경·실행 |
| 판정 | 유효성·비교 가능성·측정 차이·복잡도를 보고 유지/되돌리기/보류. 실패도 기록 |
| 계속/종료 | 예산·진행 상황·사용자 중단 조건을 확인. 현재 선택한 코드와 미확인 사항을 남김 |

## 2. 무엇을 점검하는가

모든 ML 프로젝트에 같은 전처리 목록을 강제하지 않습니다. 문제·모델·데이터 구조에 해당하는 항목만 점검합니다.

| 항목 | 확인할 근거 |
|---|---|
| 목표·지표 | 예측 단위/시점과 정답 정의, 주최측 지표와 로컬 계산의 일치 |
| 데이터 분할 | 분할 코드·표본 ID·시간/그룹 관계. 예측 상황에 맞는 분리인지 |
| 전처리 | 결측치 처리·스케일링·피처 선택 등의 학습 범위, 분할 전에 정답/검증 정보가 들어갔는지 |
| 데이터 대응 | 입력·정답 ID와 순서, 중복·누락, 학습/추론 피처의 의미와 순서 |
| 학습 | 출력·정답·loss의 대응, optimizer 갱신, 학습/평가 모드, 시드·체크포인트·조기 종료 기준 |
| 평가·추론 | 평가에 사용한 모델, 전처리 상태 재사용, 지표 집계, 제출 행/열/ID 규칙 |

코드 읽기 → 작은 데이터 검사 → 짧은 실행 → 필요한 본 실험 순서로 근거를 모읍니다. 짧은 실행 통과를 최종 성능 증거로 삼지 않습니다. 시간·그룹 구조나 예측 시점이 불명확하면 분할의 적절성을 단정하지 않습니다.

## 3. 점검 판정의 형식

각 항목은 적용 조건 / 확인한 코드·데이터·실행 / 관측 / 판정 / 한계 / 다음 행동을 가집니다.

- **확인된 문제:** 관측이 조건 위반을 뒷받침함. 비교를 무효로 만드는 문제인지도 표시.
- **의심:** 가능한 문제지만 코드나 실행 증거가 부족함. 확인 방법을 함께 기록.
- **확인 범위 내 통과:** 무엇을 검사했는지 명시. 전체 실험의 적절성을 보증하지 않음.
- **확인 불가:** 자료·실행 접근·맥락이 부족함. 통과로 바꾸지 않음.
- **해당 없음:** 적용되지 않는 이유를 기록.

점검 결과에는 확인한 코드/데이터 상태를 붙입니다. 관련 코드·분할·데이터가 바뀌면 그 결과를 오래된 상태로 표시하고 영향을 받는 항목을 재점검합니다. 모든 검사를 매번 반복할 필요는 없습니다.

## 4. 오류 수정과 성능 실험은 다르게 판단

**타당성 수정:** 누수·잘못된 지표·입력/정답 오류 등을 고칩니다. 수정 후 점수가 낮아져도 잘못된 실험으로 돌아가지 않습니다. 이전 점수는 무효 또는 비교 불가로 보존하고, 수정한 코드로 새 비교 기준을 확보합니다.

**성능 실험:** 유효한 비교 조건을 유지하면서 전처리·피처·모델·학습 전략을 바꿉니다. 여러 요소를 함께 바꾸면 효과를 한 요소의 공으로 단정하지 않습니다.

분할·지표·데이터 버전이 바뀌면 비교 구간 ID를 새로 부여합니다. 기존 실험은 삭제하지 않고 같은 조건에서 다시 실행한 기준과 비교합니다. 오류가 있는 평가 코드를 고치는 것은 가능하지만, 더 좋은 점수를 만들기 위해 비교 규칙을 바꾸는 것은 허용하지 않습니다.

## 5. 유지·되돌리기·보류

| 관측 | 판단 |
|---|---|
| 실행 실패·출력 누락·비유한 점수 | failed. 오류와 로그를 기록하고 한도 내 수정 또는 후보 포기 |
| 실행 중단·작업 상태 불명 | interrupted 또는 unknown. 성공/점수를 추정하지 않음 |
| 비교 무효·규칙 변경 | invalid 또는 not_comparable. 성능 개선으로 채택하지 않음 |
| 유효하고 같은 조건에서 의미 있는 개선 | keep. 근거와 현재 선택한 코드/산출물 연결 |
| 차이가 작거나 실행 변동을 판단할 근거 부족 | hold. 기존 선택을 유지하고 후보를 별도 보존. 필요한 반복·확인을 기록 |
| 악화되거나 이득에 비해 복잡도·비용이 큼 | discard. 자신의 변경만 되돌리고 실패 이력 보존 |
| 점수가 동등하고 코드/실행이 더 단순함 | 사전에 정한 허용 차이 안에서 keep 가능 |

지표 방향·최소 개선 폭은 `project.json.comparison`, 실행 한도는 `project.json.budget`만 원본으로 사용합니다. program.md에는 그 기준을 선택한 이유, 실행 간 변동을 확인할 방법, 복잡도 판단의 정성적 근거를 적습니다. 다음 행동의 상태 값은 `project.json.next_action`에만 기록합니다. 단일 점수만으로 차이가 확실하다고 간주하지 않습니다. 반복 실행을 못 하면 잠정 결과로 남깁니다. 모든 프로젝트에 고정된 반복 횟수나 5분 제한을 강제하지 않습니다.

실패·미제출·측정 누락의 점수는 빈 값으로 기록합니다. 낮을수록 좋은 지표에서 실패를 0점으로 기록해 최선으로 오인하지 않도록 합니다.

## 6. 로컬 검증과 대회 제출

기존 로컬 검증으로 후보를 빠르게 비교하고, 대회 점수는 실제 제출한 파일에 연결해 외부 피드백으로 기록합니다. 두 점수를 섞어 평균내거나 같은 측정으로 취급하지 않습니다.

로컬과 제출 결과가 다르면 분포·분할·과적합·구현 차이 등을 가설로 기록하고 확인합니다. 제출 점수가 낮다고 곧바로 검증 코드를 바꾸지 않습니다. 최종 평가용 데이터를 반복 선택에 사용한 뒤 독립적인 평가였다고 주장하지 않습니다.

제출 지연은 로컬 연구를 무조건 막지 않습니다. 로컬 기준에서 선택한 후보와 제출 점수 기준 후보를 각각 기록할 수 있으며, 어느 기준으로 현재 코드를 선택했는지 명시합니다. 실제 제출 동작과 규칙 확인은 [프로젝트 연결 문서](project-adapter-and-environment.md)를 따릅니다.

## 7. 기록과 종료

[Git 연구 이력](git-research-history.md)에 따라 실행할 코드 커밋을 먼저 확보하고 `experiment create --git-head`로 연결합니다. 실행 직전 코드 상태를 다시 확인하며, 관측 후 JSON과 연구 지침은 후속 커밋에 남깁니다. 결과 기록 커밋의 SHA로 code_ref를 덮어쓰지 않습니다. commit/reset/checkout은 CLI가 수행하지 않습니다.

실험별 원본은 JSON이며 [기록 템플릿](../templates/experiment.md)은 읽기용 보고서 양식입니다. 각 항목의 출처와 미기록 처리 규칙은 [보고서 필드 매핑](report-field-mapping.md)을 따릅니다. 현재 review/submission/report 명령은 미구현이며, 이를 대신해 불변 JSON을 직접 고치지 않습니다. 코드/설정, 데이터·분할, 실행 명령, 로그, 관측 점수, 판단과 다음 행동이 연결돼야 합니다. LLM에는 요약을 우선 제공하고 필요할 때 원본 로그를 읽습니다.

현재 선택한 코드와 작업 폴더에 놓인 코드를 구분합니다. hold 후보의 코드·설정·산출물을 별도로 식별해 보존하고 다음 실험을 어떤 코드에서 시작하는지 기록합니다. discard는 실험 시작 전 기록한 상태를 기준으로 후보 변경만 되돌립니다.

실행 시간 계획은 준비 검사·학습·재시도·필요한 반복을 포함합니다. 실험 횟수에서는 실행하지 않은 cancelled와 기존 실행의 정정 레코드를 제외합니다. 나머지 원실험은 planned부터 횟수를 예약하며 unknown도 확인 전에는 제외하지 않습니다. 실행 전 남은 시간/횟수를 확인합니다. 사용자가 정한 한도, 목표 달성, 반복 정체, 필수 정보 부족, 사용자 중단 시 종료하거나 해당 작업을 대기합니다. 재개 시 현재 작업 상태·코드 변경·마지막 유효 실험을 먼저 확인합니다.

## 8. 실행 포기·상태 불명·정정

실행 전에 코드가 바뀌거나 계획을 포기하면 기존 planned를 `cancelled`로 닫고 필요하면 새 ID를 만듭니다. cancelled는 실제로 시작하지 않은 실행에만 쓰며 시작/종료 시각·exit_code·score는 null, artifacts는 빈 배열, 이유 note는 필수입니다. 종료 상태이므로 다시 시작할 수 없고 실행 횟수 예산에서 제외합니다.

실행 요청 뒤 시작 여부를 확인할 수 없으면 planned에서 바로 unknown으로 기록할 수 있습니다. 이유 note와 확인 근거 evidence를 남기며 started_at은 null일 수 있습니다. unknown에서 running 또는 종료 상태로 옮기려면 기존 기록과 구별되는 새 근거가 필요하고, 이미 기록한 시각은 바꾸지 않습니다. 시작 시각이 계속 null이고 새 근거가 실제 미실행을 확인할 때만 unknown을 cancelled로 닫습니다. 상태가 불명인 채 같은 실행을 다시 시작하지 않습니다.

종료된 succeeded/failed/interrupted의 잘못된 관측은 `zar experiment correct <old-id> --file <json>`으로 새 ID에 정정합니다. 입력은 `{id, revision, execution, reason, evidence}`이며 revision은 원본의 현재 revision입니다. 원본의 계획·비교 조건·환경을 그대로 복사하고, 현재 project 설정을 섞지 않습니다. 원본 실행과 참조는 보존하며 정정 레코드에 `correction: {supersedes_id, reason, evidence}`를 남깁니다. 일반 새 레코드는 correction이 null이고 기존 v1에서 필드가 빠진 경우도 null로 읽습니다.

정정 대상은 후속 정정이 없는 활성 종료 기록만 가능합니다. 분기·순환은 금지하고, 선택 중인 실험은 먼저 `project set`으로 선택을 해제합니다. 새 execution도 succeeded/failed/interrupted여야 하며 새 decision은 null, decision_history는 []입니다. artifacts는 원본과 같게 유지하고 추가 산출물은 이후 update로만 붙입니다. 정정은 새 실행이 아니므로 횟수 예산을 추가로 쓰지 않습니다. 기존 parent/baseline/review 참조와 제출은 새 ID로 자동 이동하지 않으며, 보고서에는 예전 ID가 대체됐음을 표시합니다.

## 9. 설계 경로 확인

- 정상: 유효 기준 B → 후보 C 실행 → 같은 비교 구간에서 개선 확인 → C 유지·기록.
- 누수 수정: 기존 B의 누수 발견 → B 점수 무효 표시 → 수정 B2로 새 기준 → 이후 후보와 비교. 점수 감소로 누수 코드를 복구하지 않음.
- 실패: 후보 실행 오류 → 실패 로그·빈 점수 → 한도 내 수정 또는 자신의 변경만 되돌림.
- 제출 지연: 로컬 후보 유지 → 파일 식별자 기록 → 나중에 받은 제출 ID·점수를 같은 후보에 연결.
- 조건 변경: 분할 변경 → 이전 점수와 직접 비교 중지 → 새 구간에서 기준 확보.
- 미실행 포기: planned → cancelled → 횟수 예약 해제. 재개하려면 새 ID 생성.
- 관측 정정: 잘못된 종료 기록 → 근거를 갖춘 새 정정 ID → 원본·제출 참조 보존, 새 판단 필요.
- 중단: 작업 상태 확인 → 확인 불가면 unknown 보존 → 재개 시 확인 전 중복 실행 금지.

이 경로들은 문서 검토 사례입니다. 현재 저장소에서 ML 실험을 실행해 통과한 결과가 아닙니다.
