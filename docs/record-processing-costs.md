# 대규모 기록 처리 비용 분해

2026-10-21 · 개발 소스의 모의 연구 루프 검증입니다. 실제 API·모델 품질·요금은 검증하지 않습니다.

[기록·세션 규모별 측정](research-scale-costs.md)에서 확인한 대규모 기록 비용을 읽기·파싱·문서 검증·직렬화·해시로 나눕니다. 기록 1,000·10,000개, 완료 세션 0개에서 계획과 중단 후 재개를 측정합니다. 조회·완료 세션 최적화는 이번 변경에 포함하지 않습니다.

## 확인한 중복과 변경 범위

사전 cProfile 진단에서 계획의 5개 역할이 동일한 기록 요약을 5번 만들며, 요약의 스냅샷 식별자를 위해 전체 기록을 매번 직렬화하는 것을 확인했습니다. 이 요약은 프로젝트와 기록 및 고정된 옵션으로 결정됩니다.

`research.advance` 한 번 안에서 최대 16,384바이트 출력 예산으로 생성한 기록 요약만 재사용합니다. 매 역할의 `assert_fresh`가 프로젝트·기록을 다시 읽고 검사한 뒤, 확인된 프로젝트 해시와 기록 해시가 같을 때만 사용합니다. 키가 달라지면 새로 계산합니다. 모델 호출 전후 검사는 생략하지 않으며 전체 기록 snapshot을 역할 사이 재사용하지 않습니다. 요약을 복사해 전송 본문과 분리하고, 역할 출력·관측·비교·최근 완료 세션 기억은 매번 갱신합니다.

중단 또는 오류로 `advance`가 끝나면 요약은 버려집니다. 같은 프로세스에서 재개하더라도 새 호출은 다시 계산하며, 파일에 저장하거나 프로세스 사이에 공유하지 않습니다. 승인 토큰 생성·사용자 승인·실행·unknown 처리·중복 실행 방지·근거 기반 복구 절차는 변경하지 않습니다.

## 재현과 측정 범위

```sh
python3.11 scripts/profile_record_processing.py --source /path/to/before --output /tmp/zar-record-before --label before
python3.11 scripts/profile_record_processing.py --source . --output /tmp/zar-record-after --label after --compare /tmp/zar-record-before/summary.json
```

각 출력 경로는 새 디렉터리여야 합니다. 각 조건에 준비 실행 한 쌍 후 세 쌍을 측정합니다. 같은 런타임의 control/profiled 순서를 번갈아 실행합니다. 변경 전 소스는 `afb3512`이며 변경 전·후 런타임은 각각 고정된 복사본으로 실행합니다. 실제 전후 성능은 추가 범주 타이머가 꺼진 **control** 벽시계 중앙값을 비교합니다. control도 기존 규모 벤치마크의 로드 카운터와 결과 검증을 포함하므로 순수 CLI 시간은 아닙니다. 변경 전 전체 실행 후 변경 후 전체 실행 순서이며 두 런타임을 매 표본 교차 배치하지 않습니다. 작은 반복 결과는 환경 변동을 완전히 제거하지 못합니다.

- **읽기**: 기록 로더 내부의 `Path.read_text`. 디스크·파일 캐시 읽기와 UTF-8 디코딩을 포함합니다.
- **파싱**: 기록 로더의 strict JSON 파싱. Decimal 보존·중복 키·Unicode 검사도 포함합니다.
- **문서 검증**: 로더 내부 `validate_document`의 구조·필드 검증입니다. 프로젝트 전체의 참조·증거 검증과 같지 않습니다.
- **기록 로딩 잔여**: 디렉터리 열거·파일 안전 검사·기타 로딩 비용입니다.
- **직렬화**: codec 및 CLI·연구·맥락 모듈이 사용하는 `dumps`입니다.
- **SHA256**: 연구·맥락 모듈의 생성·update·hexdigest입니다. 모든 파일 증거 해시의 전역 계측은 아닙니다.
- **digest 잔여**: 중첩 직렬화·SHA256을 뺀 연구 digest의 UTF-8 변환 등입니다.
- **요약 생성/식별자 잔여**: 중첩 직렬화·해시 등을 제외한 각 함수 비용입니다.
- **worker 잔여**: 위 항목에 속하지 않는 측정 본문 시간입니다.

주 스레드에서 중첩 시간을 빼므로 한 표본의 범주 합은 해당 worker 본문 시간과 같습니다. **각 범주 중앙값의 합이 본문 중앙값과 같다는 뜻은 아닙니다.** 계측은 실행 시간을 늘릴 수 있으므로 profiled 값으로 속도 향상을 주장하지 않습니다. background 공급자 스레드는 별도 범주에 중복 합산하지 않습니다.

입력 생성·복사·재개 상태 준비·부모의 파일 검증은 제외합니다. 벽시계에는 프로세스 시작·import·계측 준비·CLI 본문·출력·자식의 저장 세션/토큰 검사·메타데이터 수집·종료를 포함합니다. 본문 밖 비용은 각 표본의 전체 시간에서 본문 시간을 뺀 값으로 남깁니다. RSS는 이 자식 프로세스 전체의 최고치이며 지원하지 않는 플랫폼에서는 null입니다. 파일 캐시는 따뜻한 조건이며 공개 측정 중 테스트·빌드를 병행하지 않습니다.

계획은 새 프로세스 하나에서 CLI의 start와 advance를 호출합니다. 재개는 두 역할 성공 후 세 번째 모의 호출에서 중단된 계획을 새 프로세스가 이어갑니다. 계획 5회·재개 3회 모의 호출 후 승인 대기에서 멈추며 학습은 실행하지 않습니다. 실제 프로세스 종료와 unknown 복구는 별도 통합 검사에서 검증합니다.

## 검증과 한계

전후·control/profiled에서 전체 CLI 응답의 의미 해시, 역할 순서·호출 예산·승인 토큰 재계산·기록과 이력 원문 보존을 대조합니다. 생성 ID·시각·기한·입력 해시·토큰·호출 시간만 정규화하며 상세 기준은 [규모 측정 문서](research-scale-costs.md)를 따릅니다. 소스·측정 코드·입력 해시도 저장하고 실행 중 변경을 거부합니다.

회귀 검사에서는 두 번째 역할 호출 중 실제 기록 추가·수정·삭제·정정과 프로젝트 변경, 역할 사이 변경을 주입해 차단을 확인합니다. 중단 시 호출 예산 소비와 기존 성공 응답 보존, 재개에서 요약 재생성, 오래된 입력으로 승인 거부, 새 완료 세션의 기억 반영도 확인합니다. 계측기의 중첩·예외·다른 스레드 처리와 작은 실제 프로세스의 의미 일치도 검사합니다.

`mandela` 스킬 관점에서 고정된 모의 응답으로 실제 모델 판단 품질을 입증할 수는 없습니다. 독립 기대 역할·원문 해시·부작용·기존 소스와의 응답 대조로 소프트웨어 계약을 검증하는 범위입니다. 합성 기록과 따뜻한 파일 캐시의 결과를 모든 파일 시스템·큰 본문·정정 이력에 일반화하지 않습니다. 비공개 원문·프로젝트는 실행 디렉터리의 private/에 두며 공개 자료에는 수치와 해시만 포함합니다.

## 정식 측정 결과

Python 3.11.17 · macOS arm64 · 각 조건 세 표본의 중앙값입니다. [변경 전 원자료](benchmarks/record-processing-before.json)와 [변경 후 원자료](benchmarks/record-processing-after.json)에 표본별 수치·범주·코드/입력 해시를 포함했습니다. 아래 시간·RSS·출력은 추가 범주 타이머가 꺼진 control 기준입니다.

| 기록 | 명령 | 시간 전→후 (초) | 감소율 | 최대 RSS 전→후 (MiB) | stdout 전→후 (바이트) |
|---:|---|---:|---:|---:|---:|
| 1,000 | 계획 | 1.010 → 0.942 | 6.7% | 59.05 → 58.97 | 7,588 → 7,588 |
| 1,000 | 재개 | 0.590 → 0.556 | 5.8% | 58.91 → 58.95 | 5,990 → 5,991 |
| 10,000 | 계획 | 10.076 → 9.595 | 4.8% | 363.36 → 362.95 | 7,589 → 7,586 |
| 10,000 | 재개 | 5.969 → 5.172 | 13.3% | 309.47 → 309.20 | 5,990 → 5,989 |

전후 control/profiled의 총 48개 측정 표본에서 CLI 의미가 일치하고 stderr는 0바이트였습니다. 출력에는 생성 시각·기한·호출 시간 등의 가변 메타데이터가 포함됩니다. 의미 비교에서는 앞서 명시한 가변 항목만 정규화합니다. 메모리 사용량도 관측값으로 남기지만 감소를 보장하지 않습니다.

다음은 **profiled 본문**의 비용 분해 중앙값(초)입니다. 각 항목은 중첩 비용을 제외하며 전체 비용과 성능 개선율로 직접 환산하면 안 됩니다.

| 기록 | 명령 | 읽기 전→후 | 파싱 전→후 | 문서 검증 전→후 | 직렬화 전→후 | SHA256 전→후 | 기타 본문 전→후 |
|---:|---|---:|---:|---:|---:|---:|---:|
| 1,000 | 계획 | 0.156 → 0.157 | 0.155 → 0.160 | 0.167 → 0.169 | 0.326 → 0.248 | 0.006 → 0.005 | 0.161 → 0.150 |
| 1,000 | 재개 | 0.086 → 0.088 | 0.084 → 0.091 | 0.092 → 0.095 | 0.185 → 0.147 | 0.004 → 0.003 | 0.080 → 0.078 |
| 10,000 | 계획 | 1.701 → 1.734 | 2.064 → 2.253 | 1.658 → 1.705 | 3.243 → 2.478 | 0.063 → 0.046 | 1.634 → 1.458 |
| 10,000 | 재개 | 0.976 → 0.926 | 1.267 → 1.175 | 0.936 → 0.928 | 1.852 → 1.457 | 0.038 → 0.028 | 0.841 → 0.726 |

계획의 기록 요약/식별자 생성은 **5→1회**, 재개는 **3→1회**입니다. 기록 로드는 전후 계획 **11회**(start 1회 + 역할 전후 10회), 재개 **6회**로 같습니다. 따라서 10,000개 조건의 읽기·파싱·문서 검증은 각각 계획 110,000회·재개 60,000회로 유지됩니다. SHA256 계산 자체보다 반복 직렬화 비용이 컸으며 그 중 동일한 요약 생성의 중복만 제거했습니다.

새 측정과 이전 PR의 수치는 실행 환경의 시점과 도구가 다르므로 직접 비교하지 않습니다. 현재 표의 같은 도구 전후 결과만 비교하며 작은 반복의 중앙값으로 통계적 우월성을 주장하지 않습니다. 실제 LLM 지연을 포함한 전체 시간의 개선율은 미검증입니다.

전체 회귀 **427개**가 통과했습니다. 독립 리뷰에서 런타임 변경과 측정 방법의 차단 문제는 발견되지 않았으며, 최종 원자료·문서 대조와 문서 계약·설치본 검증을 함께 수행합니다.

후속 [대규모 기록 메모리 검증](record-memory-costs.md)은 같은 읽기·파싱·검증을 유지하면서 이전 스냅샷과 다음 스냅샷의 중복 보관을 줄이고 시간·할당·RSS를 분리해 측정합니다.
