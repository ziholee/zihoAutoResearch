# 성능·규모 측정

이 문서는 성능 측정 자료의 탐색 안내와 기록 CLI의 최초 규모 측정을 함께 제공합니다. 아래 2026-10-11 계보 탐색 개선은 [v0.2.0 변경 내역](../CHANGELOG.md#020--2026-10-12-kst)에 포함되었으며 공개 v0.3.0에서도 사용할 수 있습니다. 연구 세션 관련 측정은 개발 소스 대상이며 공개 v0.3.0에는 `research` 명령이 없습니다.

측정값은 각 문서의 소스 버전·합성 입력·실행 환경에 한정됩니다. 서로 다른 실험의 시간을 이어 붙여 누적 개선율로 계산하지 않습니다. 모의 공급자의 호출 시간과 로컬 처리 비용은 실제 API 지연·청구 비용이나 ML 품질 향상의 증거가 아닙니다.

## 측정 범위와 재현

`scripts/benchmark_records.py`는 100·1,000·10,000개 합성 실험 기록을 생성합니다. 첫 기준 실험은 keep/선택 상태이며 후속 실험은 직전 실험을 parent로, 첫 실험을 baseline으로 참조합니다. succeeded/planned/failed/cancelled 상태와 hold/discard 판단, 작은 공통 해시 근거 파일을 포함합니다. 깊은 계보의 비용을 확인하기 위한 입력이며 일반 프로젝트 분포를 대표하지 않습니다. review/submission/memory/candidate 정정 이력과 큰 로그 비용은 이 측정에 포함하지 않습니다.

각 규모에서 `status`, `context`, `check`, `lineage`의 JSON 모드를 측정합니다. 명령별 워밍업 1회 뒤 새 Python 프로세스로 3회 실행하고 중앙값을 비교합니다.

- 시간: 인터프리터 시작·CLI import·검증·직렬화·파이프 출력 수집·종료를 포함한 경과 시간입니다. 데이터 생성과 결과 파일 저장은 제외합니다.
- 메모리: 자식 프로세스 자신의 `resource.getrusage(RUSAGE_SELF).ru_maxrss`입니다. macOS의 bytes, Linux의 KiB를 bytes로 정규화합니다. 누적 자식 메모리나 Python 객체 할당량이 아니며, 작은 실행 래퍼를 포함합니다. 부모 측 출력 수집 메모리는 포함하지 않습니다.
- 출력: stdout/stderr 각각의 실제 바이트 수입니다. context는 기본 envelope 상한을 유지하고, 전체 lineage와 status는 기록 수에 따라 커질 수 있습니다.
- 디스크 캐시는 비우지 않습니다. 워밍업 후의 동일 로컬 파일과 경로를 사용하며, 백그라운드 부하·파일시스템·Python·OS에 따라 결과가 달라집니다.
- 실행 전후 입력 파일 및 런타임 해시를 확인합니다. 전후 비교에서는 입력 해시, 원문 stdout/stderr 해시 및 JSON 의미 해시가 같아야 합니다.

측정 스크립트의 RSS 지원 환경은 macOS/Linux입니다. Windows CLI 지원과 회귀 CI는 유지하지만 이 스크립트로 Windows 메모리를 측정했다고 주장하지 않습니다. 런타임 의존성은 추가하지 않습니다.

```sh
# 수정 전 체크아웃과 수정 후 체크아웃을 별도 경로로 준비합니다.
python3 scripts/benchmark_records.py --source /path/to/before --output /tmp/scale-before.json --label before
# 앞 결과의 fixture_directory 값을 그대로 사용합니다.
python3 scripts/benchmark_records.py --source /path/to/after --fixtures /path/from/fixture_directory \
  --compare /tmp/scale-before.json --output /tmp/scale-after.json --label after
```

전후 소스는 `git archive` 등으로 바이트코드 캐시 없는 별도 폴더에 준비하세요. `PYTHONDONTWRITEBYTECODE`는 새 캐시 작성을 막지만 기존 `.pyc` 읽기를 막지 않으므로, 한쪽에만 캐시가 있는 체크아웃을 비교하지 않습니다.

출력 파일은 존재하지 않는 경로를 지정합니다. 스크립트가 만든 임시 데이터와 원문 출력은 재검토를 위해 남기므로 확인 후 사용자가 정리합니다. 결과의 로컬 경로는 해당 실행의 출처이며 다른 컴퓨터에 존재한다고 가정하지 않습니다.

## 2026-10-11 측정 결과

환경은 macOS 26.7.1 arm64, Python 3.14.8입니다. 기준은 dev `c6e6ba7d73f9c6cbec4a80412610434f9dc3821e`, 수정본은 아래 원자료의 runtime_digest로 식별합니다. 두 소스 복사본 모두 `.pyc` 파일이 없는 상태에서 측정했습니다. CLI 작업은 순차 실행했으며 동시 테스트·빌드는 피했습니다. 3회 중앙값은 이 환경의 관측이며 작은 시간 차이의 유의성이나 범용 성능 보장이 아닙니다.

| 100 | context | 0.081 → 0.079 | 28.73 → 28.83 | 4,574 |
| 100 | check | 0.074 → 0.079 | 28.62 → 28.75 | 1,410 |

| 1,000 | check | 0.194 → 0.158 | 35.83 → 36.12 | 11,086 |

stderr는 모든 조합에서 0바이트였습니다. 12개 조합에서 수정 전후 stdout/stderr 원문과 JSON 의미 해시가 모두 일치했고, 입력 파일도 변경되지 않았습니다. 10,000개에서는 시간이 약 5.6–8.9배 줄었습니다. 100개에서는 차이가 작고 일부 명령이 약간 느렸으므로 소규모의 개선을 주장하지 않습니다.

**메모리 절감은 확인하지 못했습니다.** status/context/check는 약 107MiB로 비슷했고, lineage는 132.64 → 136.31MiB로 약 2.8% 증가했습니다. context 출력은 약 4.5KB로 제한되지만 전체 기록을 읽는 메모리 비용은 남습니다. lineage의 약 6.3MB 전체 출력도 그대로입니다.

원자료: [수정 전](benchmarks/record-scale-before.json), [수정 후](benchmarks/record-scale-after.json). 각 파일에는 3회 개별 측정값, 워밍업, 환경, 입력·런타임·출력 해시가 있습니다. 초기 timeout polling 측정과 바이트코드 캐시 조건이 달랐던 수정 후 탐색 측정은 표에서 제외하고, 파이프 수집 방식과 캐시 없는 양쪽 복사본의 결과만 사용했습니다.

별도 [cProfile 결과](benchmarks/record-scale-profile.txt)에서는 10,000개 context의 총 15.247초 중 `inspect_project`가 누적 12.055초, 자체 9.140초를 차지했고 `set.add`가 50,045,089회 호출됐습니다. 프로파일 오버헤드가 있으므로 이 시간은 위 성능 표에 사용하지 않았습니다.

## 확인된 병목과 변경

기존 `inspect_project`는 각 실험의 parent와 baseline을 끝까지 따로 추적했습니다. 길이 N의 계보에서 공통 조상을 반복 방문해 이 부분의 작업량이 O(N²)이 됩니다. 400개 깊은 계보의 작업 횟수 검사에서 참조 접근 81,000회를 재현했습니다.

변경은 두 참조 필드의 순환 도달 여부를 한 호출 안에서 재사용하는 것에 한정합니다. 이 부분의 작업을 O(N)으로 줄이고, 순환으로 이어지는 꼬리도 기존처럼 오류를 냅니다. 원래 문서 순서에서 진단하므로 오류 문구·순서는 유지합니다. 제안된 실험 overlay도 적용한 뒤 검사하며, 영속 캐시·DB·스키마 변경은 없습니다.

검증에는 null·누락·자기 참조·순환을 포함한 작은 그래프 전체 조합, 원본을 바꾸지 않는 overlay, 재귀 한도보다 깊은 1,500개 계보의 선형 작업 상한을 사용합니다. 시간 제한을 CI 합격 기준으로 삼지 않습니다.

## 남는 한계

전체 JSON 로딩·형식/참조 검사와 context snapshot 해시는 계속 전체 기록을 사용합니다. 메모리를 일정 크기로 제한하는 변경은 아닙니다. 근거 전체 해시 읽기, 긴 정정 이력, 여러 종류의 기록 혼합, 대형 로그는 별도로 측정해야 합니다. 이번 계보 탐색 개선을 모든 명령·프로젝트의 동일한 배속이나 비용 절감으로 일반화하지 않습니다.
