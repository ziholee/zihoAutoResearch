# 기록·세션 규모별 연구 루프 비용

2026-10-21 · 개발 소스용 검증이며 실제 API 호출은 포함하지 않습니다.

기록 수와 완료 세션 수를 독립적으로 늘려 새 계획, 상태 조회, 중단된 계획 재개의 벽시계 시간·프로세스 최대 RSS·stdout/stderr 크기를 측정합니다. [기록 조회 성능](record-scale-performance.md), [CLI 시작 비용](cli-startup-costs.md)과 달리 모의 역할 호출과 저장된 계획 재개를 포함합니다.

## 범위와 보존 조건

기록 축은 완료 세션 0개를 고정하고 기록 100·1,000·10,000개를 사용합니다. 세션 축은 기록 100개를 고정하고 완료 세션 0·100·1,000개를 사용합니다. 완료 세션은 결정적인 합성 이력이며 실제 학습이 수행된 결과라고 주장하지 않습니다. 날짜와 파일 이름 순서를 반대로 만들어 최근 기억 5개의 선택·정렬을 검증합니다.

계획은 분석→평가→설계→구현 제안→검토를 거쳐 승인 대기에서 멈춥니다. 상태 조회는 저장된 승인 대기 계획을 새 프로세스에서 읽습니다. 재개 준비에서는 두 역할을 저장한 후 세 번째 모의 호출에서 제어된 중단을 발생시킵니다. 실패한 시도도 호출 예산을 소모하며, 새 프로세스가 예산을 수정하지 않고 남은 세 역할을 이어갑니다. 성공 역할 중복, 과거 기록·세션 변경, 승인 전 학습 실행은 허용하지 않습니다.

이것은 공급자 호출 중단 후 계획 재개 시험입니다. 실제 CLI 프로세스 강제 종료, unknown 보존, 근거 기반 복구 및 실행·판단 승인은 기존 [장애 복구 검증](crash-recovery-validation.md)과 전체 통합 검사에서 확인합니다. 이번 성능 시험이 이 모든 절차의 시간까지 측정한다는 뜻은 아닙니다.

## 확인된 병목과 최소 변경

1,000개 기록의 사전 cProfile 진단에서 신선도 검사와 맥락 식별자 계산의 직렬화 비용을 확인했습니다. `codec.dumps`가 문자열마다 같은 JSON 인코더 설정을 다시 준비하던 부분만 변경해, 한 번의 `dumps` 안에서 문자열·실수 인코더를 재사용합니다. Decimal 원문 숫자, 공백·이스케이프·키 순서·개행, 유한값 검사와 잘못된 키 거부는 보존합니다.

문서나 기록을 캐시하지 않으며 다음 호출·다음 프로세스로 인코더를 공유하지 않습니다. 기록 재로딩·신선도 검사·세션 탐색·승인·검토·저장·잠금·중단·재개 정책은 변경하지 않습니다. 전체 세션 읽기를 생략하는 인덱스나 캐시는 이번에 도입하지 않았습니다.

## 해석의 한계

모의 공급자는 정해진 응답을 즉시 반환합니다. 측정값은 로컬 파일·직렬화·검사·프로세스 비용이며 실제 LLM 지연·토큰·요금·판단 품질의 증거가 아닙니다. 작은 반복의 중앙값은 통계적 우월성이나 모든 프로젝트의 성능 보장이 아닙니다. 기존 합성 기록은 깊은 계보를 가지며, 큰 로그·다양한 정정 이력·큰 세션 본문은 별도 검증이 필요합니다.

`mandela` 관점에서도 고정된 모의 출력은 실제 가설 생성 능력을 검증하지 않습니다. 입력 해시·독립 기대 기억·성공 역할 순서·출력 의미·원문 보존을 대조해 이 정해진 동작과 성능을 확인하는 범위로 한정합니다.

## 측정 방법과 재현

```sh
# 변경 전 소스를 별도 디렉터리에 준비한 뒤 같은 Python으로 순서대로 실행
python3.11 scripts/benchmark_research_scale.py --source /path/to/before --output /tmp/zar-scale-before --label before
python3.11 scripts/benchmark_research_scale.py --source . --output /tmp/zar-scale-after --label after --compare /tmp/zar-scale-before/summary.json
```

출력 디렉터리는 새 경로여야 합니다. 각 조건·명령마다 준비 실행 1회 후 3회의 중앙값을 사용합니다. 입력 생성·복사·재개 상태 준비와 부모 프로세스의 파일 검증은 측정에서 제외합니다. 자식 프로세스 시작·import·로딩 계측 래퍼·CLI 출력·실행 후 세션 읽기와 승인 토큰 재검증·결과 수집·종료는 포함합니다. 최대 RSS도 이 자식 프로세스 전체의 최고치이므로 순수 CLI 메모리와 같지 않습니다. 지원하지 않는 플랫폼의 RSS는 `null`로 남깁니다.

계획은 하나의 새 프로세스 안에서 실제 CLI 진입점의 `start`와 `advance`를 연속 호출합니다. 두 명령을 별도 Python 프로세스로 호출하는 사용자 환경과는 시작 비용이 다릅니다. 조회와 재개는 각각 새 프로세스에서 CLI 진입점을 호출합니다. 재개 시간에는 앞선 두 역할과 실패 시도를 만드는 준비 시간이 포함되지 않습니다. 파일 캐시는 따뜻한 상태이며, 전후 측정 중 테스트·빌드를 병행하지 않습니다.

전후 비교는 런타임 소스와 측정 코드 해시, 생성 입력 해시를 기록하고 같은 환경·측정 코드·입력을 요구합니다. 전체 CLI JSON 응답에서 생성 세션 ID·생성 시각·기한·승인 토큰·입력 해시·호출 시간만 정규화한 의미 해시를 대조합니다. 예산·오류·다음 행동·전송량·기억과 역할 결과는 비교에 남기며, 승인 토큰은 각각 해당 소스로 다시 계산해 검사합니다. 이력과 기록의 원문 해시, 기대한 최근 기억 5개, 성공 역할의 순서도 별도로 검증합니다.

완료 이력에는 역할 출력 7개와 간소화한 trace 자리표시자를 사용합니다. 실제 상세 계측·큰 응답을 포함한 세션보다 작으므로 세션 수 결과를 실제 모든 이력에 일반화할 수 없습니다. 출력 크기는 stdout/stderr의 실제 바이트이며 가변 호출 시간의 숫자 표기로 몇 바이트 차이가 날 수 있습니다. 비공개 입력·세션·원문 출력은 실행 디렉터리의 `private/`에 두며 공개 자료에는 요약 수치와 해시만 포함합니다.

## 남은 비용과 다음 판단

완료 세션 1,000개 조건에서는 계획 중 세션 로드 5,010회, 재개 중 3,006회를 관측합니다(주 스레드의 계측 대상 함수 호출 수). 각 역할의 최근 기억을 만들 때 이력을 다시 읽는 비용이 남아 있습니다. 같은 조건에서 기록 로드는 계획 11회·재개 6회이며 조회는 기록을 읽지 않고 선택 세션을 한 번 읽습니다. 다음 개선 후보는 이 반복 로딩이지만, 수정·삭제·정정된 이력과 새 세션을 놓치지 않는 신선도 계약을 먼저 검증해야 합니다. 이번에는 캐시나 인덱스를 추가하지 않았습니다.

규모에 따라 응답 본문을 전체 기록만큼 키우지 않으며 최근 기억 선택과 승인 대기 상태를 유지합니다. 출력 크기가 일정하다는 결과는 모델의 실제 토큰 사용량이나 품질을 뜻하지 않습니다. 실제 공급자 연결 검증은 사용자 요청에 따라 계속 보류합니다.

## 검증

전체 회귀 417개, 신규 규모 프로토콜 검사 2개와 문서 계약을 확인합니다. 직렬화 회귀는 수정 전 반복 인코더 생성으로 실패하고 수정 후 통과하며, 추가로 2,000건의 전후 직렬화 바이트를 대조했습니다. 설치된 wheel·sdist의 합성 학습·승인·중단·재개·장애 복구 시나리오도 검증합니다. 독립 리뷰에서 전체 CLI 응답 비교와 측정 범위 설명을 보완했습니다. 실제 API는 호출하지 않았습니다.

후속 [대규모 기록 처리 비용 분해](record-processing-costs.md)에서는 호출 전후 신선도 검사를 유지하면서 동일한 기록 요약의 반복 생성만 줄입니다. 이 문서의 표는 해당 후속 변경 이전 측정값으로 보존합니다.

후속 [완료 세션 반복 조회](completed-session-costs.md)에서는 같은 내용의 strict JSON 파싱 중복만 줄입니다. 이 문서의 과거 측정값은 변경하지 않습니다.
