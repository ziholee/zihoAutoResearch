# 기록 식별자 직렬화 비용

2026-10-22 · 합성 기록과 모의 공급자만 사용합니다. 실제 API·학습 성능은 검증하지 않습니다.

## 원인과 변경

`codec.dumps`는 딕셔너리 키가 문자열인지 먼저 검증한 뒤, 같은 키를 다시 일반 값용 재귀 함수에 전달했습니다. 이 함수의 Decimal·정수·실수·문자열 타입 분기가 이미 검증된 키에도 반복됐습니다. 검증된 키만 기존 scalar encoder로 직접 보내 이 중복을 제거합니다. 값 처리와 키 검증, 삽입 순서, 공백·줄바꿈, Unicode 설정, Decimal 표현 및 비유한 숫자 거부는 유지합니다.

키 인코딩 캐시도 진단했지만 항목·문자열 크기·타입 제한 비용을 포함하면 직접 호출보다 유리하지 않았습니다. 새 캐시나 기록 재사용은 도입하지 않습니다. 호출 전후 원문 읽기·파싱·검증·해시와 최근 기억·승인·중단·재개 절차를 유지합니다.

## 측정 구분과 재현

현재 구현에는 별도의 정규화 트리 복사 단계가 없습니다. 순회·타입/키 검사·JSON 조립이 재귀 함수 안에 결합돼 있으므로 이를 독립적인 정규화 시간으로 표현하지 않습니다.

```sh
# before에는 기준 커밋 ed379bd의 별도 소스 사본을 사용합니다.
python3.11 scripts/profile_record_serialization.py --before /tmp/before --after . --output /tmp/serialization --records 100 10000 --repeats 3
```

공통 합성 fixture의 기록을 각 소스의 검증기로 로드한 뒤 측정합니다. 각 모드·소스·반복은 새 프로세스이며 준비 1회 뒤 3회 측정하고 전후 실행 순서를 번갈아 바꿉니다.

- `control`: 실제 `codec.dumps`, UTF-8 인코딩, SHA256 시간을 구분합니다. 시작·로딩·검증·파일 저장 시간은 제외하므로 CLI 지연이 아닙니다.
- `scalar-profile`: 실제 scalar encoder의 시간·호출 수를 측정하고 나머지를 순회·검사·조립 잔여로 표시합니다. 계측 오버헤드가 있어 control과 구분합니다.
- `allocation`: 별도 tracemalloc 실행으로 일시 할당을 관찰합니다. 입력 기록 로딩 후 추적을 시작하므로 전체 기록 메모리나 RSS가 아닙니다. 문자열과 UTF-8 bytes가 함께 존재하는 구간을 기록하고 해시 전 문자열을 해제합니다.

모든 worker의 문자열 인코딩 결과를 직접 바이트 비교하고 SHA256도 대조합니다. 원문은 `private/`에만 남기며 공개 보고서는 수치·해시만 포함합니다.

## 직렬화 단독 결과

Python 3.11.17·Darwin arm64, 3회 중앙값입니다. [전체 단계별 표본](benchmarks/record-serialization-profile.json)을 제공합니다.

| 기록 수 | 직렬화 전→후(초) | UTF-8 전→후(초) | SHA256 전→후(초) | 별도 추적 할당 최고 전→후(bytes) |
| --- | ---: | ---: | ---: | ---: |
| 100 | 0.002105 → 0.001691 | 0.000040 → 0.000041 | 0.000048 → 0.000049 | 549,591 → 549,399 |
| 10,000 | 0.214304 → 0.176523 | 0.003764 → 0.003627 | 0.003640 → 0.003334 | 54,786,261 → 54,786,069 |

10,000개 직렬화 시간은 이 조건에서 약 17.6% 줄었습니다. 추적 할당은 사실상 같아 메모리 개선으로 해석하지 않습니다. 각 항목 중앙값의 합은 표본별 전체 시간의 중앙값과 다를 수 있습니다.

별도 scalar-profile의 10,000개 인코더 호출 수는 전후 752,507회로 같습니다. scalar 시간 중앙값은 0.080712→0.078753초, 순회·검사·조립 잔여 시간은 0.273780→0.232948초였습니다. quoting 호출 자체를 생략한 것이 아니라 그 앞의 중복 일반 타입 분기를 제거한 결과와 일치합니다. 이 값에는 계측 오버헤드가 있으므로 위 control 시간에 더하지 않습니다.

100개 결과 112,306bytes, 10,000개 결과 11,221,990bytes가 모든 전후/계측 모드에서 직접 비교로 일치했습니다. 공백만 바뀌어도 측정 도구가 거부하는 회귀 검사를 추가했습니다.

## 전체 루프 검증

작은 조건은 기록 100개·완료 세션 0개, 혼합 조건은 기록 10,000개·완료 세션 2,500개·기억 본문 16,000자입니다. 기존 벤치마크를 변경 없이 사용합니다.

```sh
python3.11 scripts/benchmark_research_scale.py --source /tmp/before --output /tmp/small-before --records 100 --sessions 0 --repeats 3
python3.11 scripts/benchmark_research_scale.py --source . --output /tmp/small-after --records 100 --sessions 0 --repeats 3 --compare /tmp/small-before/summary.json
python3.11 scripts/benchmark_session_boundaries.py --source /tmp/before --output /tmp/mixed-before --records 10000 --cases large-memory --repeats 3
python3.11 scripts/benchmark_session_boundaries.py --source . --output /tmp/mixed-after --records 10000 --cases large-memory --repeats 3 --compare /tmp/mixed-before/summary.json
python3.11 scripts/verify_mixed_research.py --source . --output /tmp/mixed-verification
```

CLI 시간에는 프로세스 시작·출력·저장된 토큰 검증·종료 등이 포함되며 fixture 생성·복사·재개 준비는 제외합니다. 각 행 준비 1회 뒤 3회 측정합니다. 재개는 모의 요청 중단 뒤 별도 프로세스가 저장된 성공 역할 2개를 보존하고 나머지 3개를 수행합니다. OS 강제 종료나 실제 학습의 성능 측정은 아닙니다. 기존 강제 종료·unknown·복구 회귀 검사는 유지합니다.

정식 측정 중 다른 테스트·빌드를 병행하지 않습니다. 소스·측정 코드·입력 해시와 CLI 의미, 최근 기억·역할·예산·승인·원문 보존을 확인합니다. CLI는 전 실행 후 후 실행 순서이므로 시간대·파일 캐시 변동 한계가 남습니다. 직렬화 단독 개선율을 전체 루프 개선율로 적용하지 않습니다.

## 전체 루프 결과

각 값은 3회 중앙값이며 시간과 RSS를 별도로 집계합니다. 작은 조건은 [전](benchmarks/record-serialization-small-before.json)·[후](benchmarks/record-serialization-small-after.json), 혼합 조건은 [전](benchmarks/record-serialization-mixed-before.json)·[후](benchmarks/record-serialization-mixed-after.json) 원시 표본을 제공합니다.

| 조건 | 작업 | 시간 전→후(초) | 최고 RSS 전→후(MiB) |
| --- | --- | ---: | ---: |
| 기록 100개·세션 0개 | 계획 | 0.1937 → 0.1908 | 38.00 → 38.02 |
| 기록 100개·세션 0개 | 조회 | 0.0905 → 0.0894 | 36.00 → 35.95 |
| 기록 100개·세션 0개 | 재개 | 0.1476 → 0.1453 | 37.83 → 37.83 |
| 기록 10,000개·큰 기억 2,500개 | 계획 | 10.4239 → 10.0200 | 301.91 → 301.97 |
| 기록 10,000개·큰 기억 2,500개 | 조회 | 0.0915 → 0.0997 | 35.92 → 35.97 |
| 기록 10,000개·큰 기억 2,500개 | 재개 | 5.8467 → 5.6707 | 247.77 → 227.75 |

작은 조건의 기존 도구는 기록 축과 세션 축을 각각 실행하므로 같은 100개·0세션 조합을 두 번 포함합니다. 표는 기록 축이며 두 축의 모든 표본을 공개합니다. 총 CLI 측정 54개와 준비 실행 18개에서 동일 의미·입력 보존 검증을 통과했습니다. 표준 출력은 계측 수치가 들어가 크기가 조금 달라질 수 있으나 의미 해시는 전후 일치합니다.

혼합 계획은 약 3.9%, 재개는 약 3.0% 짧게 관측됐지만 조회는 약 8ms 늘었습니다. 전체 속도의 일괄 향상이나 통계적 유의성을 주장하지 않습니다. 재개의 최고 RSS 중앙값도 낮게 나왔으나 변경 후 표본이 227.70–238.50MiB로 달랐고 직렬화 추적 할당은 사실상 같습니다. 이를 구조적인 메모리 절감 효과로 해석하지 않습니다.

## 검증

기존 소스에 새 타입 분기 회귀를 적용하면 키 100개에 500번의 타입 검사로 실패하고, 변경 후 문자열 검증 100번만 수행해 통과합니다. Unicode/ASCII, Decimal 표현, 많은 고유 키·큰 키, 삽입 순서와 SHA256 동등성도 확인합니다. 전체 465개 테스트가 통과했습니다.

10,000개 기록·큰 기억 2,500개에서 [변경 감지·승인·재개 9개 시나리오](benchmarks/record-serialization-verification.json)도 모두 통과했습니다. 같은 크기·mtime 수정, 추가·삭제·정정, 이력 갱신과 최근 5개 동률 선택, 성공 역할 보존, 승인 전 실행 거부 및 오래된 입력의 승인 거부를 확인했습니다.

## 한계

한 로컬 환경, 합성 자료, 따뜻한 파일 캐시, 소수 반복의 결과입니다. 최고 RSS와 추적 할당은 다른 지표이며 메모리 상한을 보장하지 않습니다. 큰 문자열 조립·UTF-8 인코딩의 일시 할당은 이번 최소 변경으로 제거되지 않습니다.
