# macOS CI 비용 분해

검사 범위를 유지하면서 CI의 자식 프로세스·서버 종료·반복 준비 비용을 확인합니다. 실제 API 호출이나 모델 품질 검증은 포함하지 않습니다.

## 측정 방법

기존 전체 unittest 명령과 OS/Python 행렬을 그대로 실행합니다. `ZAR_CI_COST_DIR`을 지정하면 두 통합 검사가 성공한 뒤 기존 임시 결과에서 수치만 추출합니다. 별도의 실험 루프를 더 돌리지 않으며 기존 승인·실제 학습·새 프로세스 재개·증거 변조 검사는 모두 수행합니다.

- `workflow-utility.json`: 두 번의 direct/zar 비교 각각의 CLI·Git·학습 자식 프로세스·서버 종료·나머지 시간과 횟수입니다. 초기 준비 단계의 시간과 그 안의 명령 시간을 제외한 준비 잔여도 남깁니다.
- `local-loop-costs.json`: 기존 baseline/profiled/short_poll 세 조건을 그대로 보존합니다. profiled 조건에서 Python 자식 시작·import/계측 준비와 본문·종료 잔여를 나눕니다.
- `environment.json`: 요청을 보내지 않고 Python 빈 자식·CLI import 자식·urllib opener 생성을 각 3회 측정합니다. 순수 OS 프로세스 생성 시간은 아니며 대기·출력 수집·종료를 포함합니다.

두 통합 검사에는 전체 검사 시간과 워커 시간 합계를 뺀 `verification_and_test_overhead_seconds`도 기록합니다. 이 잔여에는 Git 증거 검증·추가 단언·부모 실행·준비가 섞여 있으므로 순수 검증 시간이라고 해석하지 않습니다. 진단 파일 저장과 임시 폴더 정리는 해당 전체 검사 타이머 밖입니다.

`phase_diagnostics_seconds`와 `setup_other_seconds`는 배타 분할과 겹치는 진단입니다. provider·commit 이벤트도 CLI/Git 시간 안에 포함될 수 있으므로 합산하지 않습니다. 각 표본의 배타 분할 합은 해당 표본의 전체 시간과 같으며, 항목별 중앙값 합은 전체 중앙값과 다를 수 있습니다.

CI는 `ci-costs-<OS>-<Python>` 아티팩트를 7일 보존합니다. 고정 필드의 수치·버전·소스 해시만 저장하고 명령 인자·응답 본문·인증정보·실험 원문·로컬 경로는 복사하지 않습니다. 실패한 통합 검사는 성공 보고서를 만들지 않을 수 있으며, 성공한 검사의 진단은 `always()` 업로드로 보존합니다. 진단이 없으면 시간 0으로 간주하지 않습니다.

## 로컬 재현

```sh
ZAR_CI_COST_DIR=/tmp/zar-ci-costs python3.11 -m unittest discover -s tests -v
python3.11 scripts/profile_ci_environment.py --output /tmp/zar-ci-costs/environment.json
```

비교할 실행마다 새 출력 폴더를 사용합니다. 공개 성능 비교 중에는 다른 테스트·빌드를 병행하지 않습니다. GitHub 호스팅 러너와 로컬 장치, Python 배포판은 다르므로 두 환경의 수치를 같은 조건의 전후로 비교하지 않습니다.

## 범위와 한계

PR #50의 macOS CI는 12분 56초였고 제한은 15분입니다. 로그상 효용 비교 검사 인접 출력 간격은 약 289초, 로컬 비용 검사 구간은 약 222초였습니다. 이는 원인 진단 전의 구간 관측이며, 특정 함수의 독점 비용이나 순수 테스트 시간은 아닙니다.

초기 진단 workflow는 job-level 환경변수에서 `runner.temp`를 참조해 GitHub 파싱 단계에서 거부됐습니다. 이를 step-level 환경변수로 옮긴 뒤 기준 실행을 시작했습니다. 실패한 설정 실행은 성능 비교에 포함하지 않습니다.

## 확인된 중복의 최소 변경

`verify_arm`의 baseline/candidate가 같은 HEAD 증거 경로를 각각 조회했습니다. 한 번의 검증 안에서 경로 합집합을 만든 뒤 모든 고유 경로의 Git blob과 현재 파일 원문을 대조합니다. 과거 소스 커밋 2개·Git 이력 수·점수·역할·승인·재개·변조 검사도 유지합니다. 검증 호출 사이에 blob을 캐시하지 않습니다.

실제 완료 fixture에서 zar는 Git 자식 19→18회, direct는 19→15회입니다. mock 회귀 fixture의 zar 증거 구조는 실제 runner가 만든 로그 참조와 다르므로 mock 호출 수를 실제 실행 수로 대체하지 않습니다. 새 회귀는 독립적으로 지정한 고유 경로가 빠짐없이 한 번씩 대조되는지, 다음 검증에서 Git 증거가 바뀌면 거부하는지 검사합니다. 반복 실험·설정별 준비·20개 CLI 명령·14개 역할 요청·학습 2회·승인 4회·새 프로세스 재개는 줄이지 않습니다.

중복 조회 감소를 CI 전체 지연 해결로 해석하지 않습니다. 실제 macOS 진단으로 병목과 변화 범위를 별도로 확인합니다.

## 동일 fixture의 로컬 대조

Python 3.14.6 · macOS arm64에서 완료된 동일 zar fixture를 변경 전(`4b51db9`)·후(`d05ffed`) 검증 함수로 번갈아 검사했습니다. 준비 1쌍 뒤 5쌍을 측정하고 fixture 전체 바이트 해시와 반환 검증 결과가 같은지 확인했습니다. 양쪽 모두 같은 subprocess 호출 카운터를 적용했으며 테스트·빌드를 병행하지 않았습니다.

검증 함수 중앙값은 **0.1954→0.1830초**, Git 자식 호출은 **19→18회**였습니다. [원자료](benchmarks/ci-verifier-local.json)에 개별 표본·함수 소스 해시·fixture 해시를 남겼습니다. 이 작은 차이는 해당 로컬 검증 함수의 관측값이며 CI 전체 개선율이 아닙니다. 다른 기기·파일 캐시·증거 크기에 일반화하지 않습니다.

## 실제 macOS 원인 확인

[기준 CI 원자료](benchmarks/macos-ci-before.json)는 `4b51db9`의 실행 [39593526762](https://github.com/ziholee/zihoAutoResearch/actions/runs/39593526762)에서 얻었습니다. 효용 비교 검사는 290.47초였지만, 각 워커의 준비 잔여가 약 35.02초, 재개에도 약 35초가 반복됐습니다. 로컬 비용 검사의 세 조건 역시 각 73초 중 약 70.3초가 CLI·Git·종료 밖의 잔여였습니다. profiled CLI 시작 합계는 1.728초, 본문 저장은 0.060초였으므로 이 둘이 수백 초 지연의 주원인은 아니었습니다.

표준 `HTTPServer` 생성 중 hostname 조회를 별도로 계측한 [진단 자료](benchmarks/macos-ci-hostname-probe.json)에서 총 **35.013134초 중 `socket.getfqdn`이 35.012793초**, 나머지는 0.000342초였습니다. 이 진단 실행은 환경 아티팩트를 확보한 뒤 중복되는 나머지 통합 실행을 중단했습니다. 최종 성공 CI를 대체하지 않습니다.

고정 숫자 루프백 주소를 사용하는 benchmark 전용 서버에서는 이 역방향 호스트명 조회를 반복할 필요가 없습니다. `TCPServer.server_bind`를 통해 실제 바인딩·동적 포트 선택·주소 재사용은 유지하고, 표시용 서버 이름만 `localhost`로 지정합니다. HTTP 처리·직접 실행/zar 비교·동일 포트의 새 프로세스 재개는 유지합니다. 실제 공급자 통신과 제품 DNS 처리는 바꾸지 않습니다.

최종 CI 환경 프로브에서 느린 표준 hostname 조회는 기본 실행하지 않습니다. 원인 재현이 필요하면 `python scripts/profile_ci_environment.py --hostname-probe --output /tmp/hostname.json`으로 명시적으로 실행할 수 있습니다. 기본 진단과 기존 통합 검사 범위는 그대로 유지합니다.

## 실제 CI 전후 결과

동일한 GitHub `macos-latest`·Python 3.14.8 설정에서 기준 실행과 최종 [실행 39596069911](https://github.com/ziholee/zihoAutoResearch/actions/runs/39596069911)을 비교했습니다. [최종 원자료](benchmarks/macos-ci-after.json)는 서버 개선까지 포함한 `3a2904f` 기준입니다. 두 실행은 서로 다른 호스팅 러너의 **각 한 번 관측**으로, 반복 교차 실험이나 통계적 개선 보장은 아닙니다.

| 구간 | 변경 전 (초) | 변경 후 (초) |
|---|---:|---:|
| macOS unittest 본문 | 777.565 (442개) | 248.143 (446개) |
| macOS job 전체 | 788 | 258 |
| 효용 비교 통합 검사 | 290.471 | 6.772 |
| 비용 분해 통합 검사 | 221.133 | 8.110 |
| 효용 비교 초기 준비 잔여 범위 | 35.012~35.030 | 0.0013~0.0023 |
| 비용 분해 profiled 조건의 워커 잔여 | 70.298 | 0.215 |

전체 검사 수가 늘어난 것은 새 Git 경로 회귀 2개와 서버 회귀 2개 때문입니다. 기존 검사 삭제·skip·반복 축소는 없습니다. 각 통합 검사의 진단 시간에는 보고서 생성·임시 폴더 정리가 제외되며 job 시간은 환경 설치·진단·업로드도 포함합니다.

다음은 비용 분해의 **profiled 조건 한 표본**입니다. 본문 계측 자체에 오버헤드가 있으므로 순수 비계측 성능으로 취급하지 않습니다.

| 배타 구간 | 전 (초) | 후 (초) |
|---|---:|---:|
| CLI 자식 전체 | 2.753 | 1.871 |
| 외부 Git | 0.245 | 0.129 |
| 서버 종료 | 0.153 | 0.433 |
| 워커 잔여(준비 포함) | 70.298 | 0.215 |
| 합계 | 73.449 | 2.648 |

CLI 안의 시작·import·계측 준비는 1.728→1.182초, 저장은 0.060→0.028초였습니다. 이는 CLI 전체와 **중첩되는 세부 값**입니다. 서버 종료 시간은 오히려 증가했고 이 설정의 poll 간격은 바꾸지 않았습니다. 짧은 종료 poll 조건도 그대로 유지합니다. 큰 감소는 직접 계측으로 확인한 반복 hostname 조회 제거와 일치하지만, 작은 CLI·Git·종료 차이까지 이번 변경의 효과로 귀속하지 않습니다.

전후 원자료의 역할 요청·CLI·학습·Git milestone·승인·종료 횟수는 같습니다. 각 arm의 역할 요청 14회·학습 2회·승인 4회, zar CLI 20회와 새 프로세스 재개·증거 변조 검사를 유지합니다. 워크플로 수치를 추출한 helper·기존 통합 검사·제품 소스 해시는 동일하고 benchmark 구현만 달라졌습니다. 환경 프로브는 별도 진단이며 선택적 hostname 계측이 추가됐습니다. zar의 학습은 CLI 내부에서 실행되므로 외부 `training` 이벤트는 0이지만 기존 검사는 실행 원장으로 2회를 확인합니다.

로컬 Python 3.14.6 전체 **446개**와 실제 CI의 모든 OS·문서·설치 검증이 통과했습니다. 로컬 설치본 검증도 실제 합성 학습·HTTP·승인·중단/재개·복구를 확인합니다. 실제 API 연결은 보류합니다. 다른 예제 서버의 비용까지 이번 결과로 일반화하지 않습니다.
