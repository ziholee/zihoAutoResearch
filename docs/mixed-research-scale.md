# 대규모 기록과 큰 완료 세션의 혼합 검증

2026-10-22 · 모의 공급자와 합성 기록 기준입니다. 실제 API의 지연·요금·모델 판단 품질은 검증하지 않습니다.

## 조건과 측정 범위

기존 [대규모 기록 메모리](record-memory-costs.md)와 [큰 완료 세션](session-cache-boundaries.md)을 같은 프로젝트에서 함께 검증합니다. 성능 측정은 기존 `benchmark_session_boundaries.py`를 변경 없이 사용하고 기록 수를 10,000개로 설정합니다.

- 큰 일반 응답: 완료 세션 16개, 각 1MiB. 기억 외 여섯 역할의 응답 필드에 본문을 분산합니다.
- 큰 기억: 완료 세션 2,500개, 각 `memory.lesson` 16,000자. 최근 5개만 요청에 포함합니다.

모든 합성 역할 출력은 기존 역할 검증기를 통과하며 세션 파일 크기 제한을 지킵니다. 이는 문법을 만족하는 합성 자료이지 실제 학습 결과나 모델 판단의 품질을 뜻하지 않습니다. 2,048개·8MiB 캐시 한도는 입력 보관 범위이며 프로세스 RSS 상한이 아닙니다.

```sh
python3.11 scripts/benchmark_session_boundaries.py --source . --output /tmp/mixed-scale --records 10000 --cases large-responses large-memory --repeats 3 --label mixed
```

각 조건의 계획·조회·재개는 준비 실행 1회 뒤 3회 측정합니다. 계획은 5개 역할 뒤 승인 대기까지, 조회는 저장된 승인 대기 상태를 확인합니다. 재개는 2개 성공 역할을 저장한 뒤 세 번째 모의 요청에서 중단하고 새 프로세스가 나머지 3개 역할을 수행합니다. 시간은 Python 시작·CLI·출력·저장 상태/승인 토큰 검증·메타데이터 기록·출력 수집·종료를 포함합니다. 입력 생성·복사·재개 준비·부모 검증은 제외합니다. RSS는 측정 자식 전체의 최고치입니다.

정식 측정 중 다른 테스트·빌드를 병행하지 않습니다. 입력·소스·측정 코드 해시, 최근 기억 순서, 역할·예산·승인 토큰, CLI 의미와 기록·이력 원문 보존을 대조합니다. 기존 자료는 실행 시점과 측정 범위가 달라 혼합 조건의 증가율이나 개선율을 직접 계산하는 기준으로 사용하지 않습니다.

## 측정 결과

Darwin arm64·Python 3.11.17, 각 행 3회 중앙값입니다. 총 18개 측정 표본과 6개 준비 실행을 검증했습니다. [전체 표본과 해시](benchmarks/mixed-research-scale.json)를 함께 제공합니다. 시간·RSS·출력 중앙값은 각 항목에서 따로 계산합니다.

| 완료 세션 조건(기록은 모두 10,000개) | 작업 | 시간(초) | 최고 RSS(MiB) | stdout(bytes) |
| --- | --- | ---: | ---: | ---: |
| 일반 응답 16개 × 1MiB | 계획 | 9.4448 | 298.81 | 7,587 |
| 일반 응답 16개 × 1MiB | 조회 | 0.0957 | 36.00 | 5,554 |
| 일반 응답 16개 × 1MiB | 재개 | 4.9602 | 244.55 | 5,991 |
| 큰 기억 2,500개 × 16,000자 | 계획 | 10.4674 | 302.91 | 7,597 |
| 큰 기억 2,500개 × 16,000자 | 조회 | 0.0940 | 36.03 | 5,562 |
| 큰 기억 2,500개 × 16,000자 | 재개 | 5.7095 | 247.62 | 6,002 |

큰 기억 조건의 세션 입력은 총 46,290,000bytes(세션당 18,516bytes)입니다. 입력 크기 기준 캐시 보관 예상치는 일반 응답 8개/8,388,608bytes, 큰 기억 453개/8,387,748bytes입니다. 이는 객체 메모리를 직접 측정한 값이 아닙니다. 큰 기억 계획의 RSS 표본은 267.92–302.97MiB로 변동했으며 중앙값만으로 메모리 상한을 보장하지 않습니다.

모든 표본에서 최근 5개 기억, 성공 역할 보존, 승인 대기·토큰, 호출 예산과 CLI 의미 해시를 확인했습니다. 원본 기록·완료 이력도 보존됐습니다. 계획은 모의 호출 5회, 조회는 0회, 재개는 나머지 3회이며 중단된 요청을 포함한 저장 예산은 6회입니다.

## 개선 판단

이번 변경은 검증 도구·회귀 검사·문서에 한정합니다. 혼합 조건 조사에서 추가로 제거할 중복을 확인하지 못해 `zar/` 실행 코드와 캐시 한도를 바꾸지 않았습니다. 기존 최근 기억 선택 및 스냅샷 해제 개선을 유지합니다. 위 수치는 현재 구현의 관측값이며 전후 개선 효과를 주장하는 자료가 아닙니다.

다음 성능 조사는 기록 식별자 직렬화의 시간·일시 할당을 분해하는 것이 우선입니다. 출력 바이트·해시·호출 전후 변경 감지를 유지하면서 중복이 입증되는 경우에만 개선합니다. 현재 측정만으로 파일 검사 생략이나 캐시 한도 확대를 정당화하지 않습니다.

## 변경 감지와 승인 검증

성능 측정의 입력은 고정합니다. 별도 `verify_mixed_research.py`는 혼합 자료를 의도적으로 수정해 변경 감지·최근 기억 갱신·승인·중단 후 재개를 검증합니다. 변조 실행은 성능 표본에 넣지 않습니다. 원문과 명령 출력은 실행 폴더의 `private/`에 두고 공개 보고서에는 수치·검증 결과·해시만 남깁니다.

```sh
python3.11 scripts/verify_mixed_research.py --source . --output /tmp/mixed-verification
```

기본 조건은 기록 10,000개·완료 세션 2,500개·기억 본문 16,000자입니다. 성능 fixture와 별도로 여섯 세션의 생성 시각을 같은 값으로 설정하고, 시각과 식별자의 명시적 정렬로 최근 5개 기대값을 구합니다. 제품의 기억 선택 함수를 기대값 생성에 사용하지 않습니다.

| 시나리오 | 확인하는 계약 |
| --- | --- |
| 기록 수정·추가·삭제·정정(4개) | 두 번째 응답 도중 입력이 바뀌면 해당 응답을 폐기하고 첫 성공 응답과 호출 예산을 보존 |
| 역할 사이 기록 수정 | 다음 공급자 호출 전에 변경을 감지 |
| 이력 수정·추가·삭제 | 다음 요청에 최신 기억과 동률 순서를 반영; 수정은 크기·mtime을 유지 |
| 중단 후 별도 프로세스 재개 | 저장된 성공 역할 2개를 보존하고 바뀐 기억으로 나머지 3개만 호출; 중단 시도까지 총 6회로 계산 |
| 정상 승인 | 승인 전 실행과 잘못된 토큰을 거부하고 정확한 토큰으로 승인 |
| 오래된 입력의 승인 | 계획 뒤 기록이 바뀌면 기존 토큰으로 승인하지 못함 |

기록 수정도 파일 크기·mtime을 유지합니다. 각 시나리오는 독립 fixture와 새 프로세스를 사용하며 학습 명령을 실행하지 않습니다. 작은 CI fixture(기록 2개·세션 6개)로 같은 9개 경로를 회귀 검사합니다.

## 검증 결과

전체 규모의 9개 시나리오가 모두 통과했습니다. [기능 검증 보고서](benchmarks/mixed-research-verification.json)에 조건·소스/도구 해시·호출 수·검증 flags를 기록했습니다. 작은 fixture를 포함한 전체 테스트 459개도 통과했습니다. 정식 성능 측정은 테스트 종료 뒤 단독 실행했으며, 테스트와 시작 시점이 겹칠 가능성이 있던 최초 실행은 중단하고 결과에서 제외했습니다.

## 해석의 한계

한 로컬 환경·합성 자료·따뜻한 파일 캐시·소수 반복의 관측입니다. 다른 파일 시스템·OS·실제 연구 문서·실제 공급자에 일반화하지 않습니다. 모의 요청 중단 후 재개이며 OS 강제 종료·실제 학습·복구의 성능은 이번 측정 범위가 아닙니다. 기존 기능 검사의 승인·실제 자식 종료·unknown 보존·근거 기반 복구 검증은 유지합니다.

후속 [기록 직렬화 비용](record-serialization-costs.md)은 동일한 변경 감지 계약을 유지한 최소 개선과 작은·혼합 조건의 대조 측정을 다룹니다.
