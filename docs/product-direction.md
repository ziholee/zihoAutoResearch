# 제품 정의와 설계 방향

갱신: 2026-10-07 · 현재 사용자 방향을 반영한 설계

## 1. 목표

zihoAutoResearch는 LLM이 기존 ML 프로젝트를 이해하고 전처리·학습·검증의 타당성을 점검하며, 실행 가능한 코드 변경과 실험을 통해 전체 파이프라인을 개선하도록 돕습니다.

사용자는 이미 가진 코드·데이터·실행 환경을 활용합니다. 대회 프로젝트에서는 주최측의 문제 정의·데이터·평가 지표·제출 형식을 따릅니다. 검증셋이 없다면 학습 데이터의 구조에 맞춰 로컬 분할을 정합니다. 별도 데이터 제공·채점 플랫폼은 만들지 않습니다.

## 2. 제품의 형태

초기 형태는 기존 LLM 코딩 에이전트가 읽는 연구 지침, 필요한 작은 검사 도구, 프로젝트 안에 남는 실험 기록입니다. 별도 LLM 서버·상주 실행 서비스·그래프 프레임워크를 먼저 구축하지 않습니다. 단계와 분기는 명시하되 구현을 특정 프레임워크에 묶지 않습니다. 영속 상태는 JSON/Git, 명령별 읽기는 공통 기록 스냅샷, 재개 정보는 context, 원문 확인은 evidence read가 담당합니다. [조회 구조](context-and-evidence.md)는 기존 기록을 파생 조회하며 별도 기억 DB를 만들지 않습니다.

[Git 연구 이력](git-research-history.md)을 기본 작업 방식으로 삼습니다. 코드·설정을 먼저 커밋하고 실험 JSON이 해당 SHA를 참조하며, 결과와 판단은 후속 기록 커밋으로 보존합니다. Git은 실행 환경을 대체하거나 ML 타당성을 보증하지 않습니다.

사람은 목표·제약·작업 범위를 정합니다. LLM은 코드와 관측을 읽고 점검·가설·수정을 수행합니다. 수치와 실행 사실은 기존 검사·로그·예측·채점 결과로 확인합니다. LLM의 설명만으로 성공을 기록하지 않습니다.

## 3. AutoResearch에서 가져오는 것

| 원본의 접근 | 우리 설계에서의 적용 |
|---|---|
| 사람이 작성하는 program.md | LLM이 프로젝트에서 초안을 만들고 확정된 목표·명령·변경 범위를 기록 |
| 원본 실행으로 baseline 확보 | 기존 실행과 검증 타당성을 확인하고 유효한 비교 기준 확보 |
| 수정 → 실행 → 지표 확인 → 기록 → 유지/폐기 | 같은 비교 조건과 실행 근거를 확인한 뒤 유지·되돌리기·보류 |
| 변경하지 않는 평가 코드 | 비교 구간 동안 분할·지표·평가 방법 고정 |
| 단순한 변경을 선호 | 비슷한 성능이면 복잡도·실행 비용이 낮은 변경을 선호 |

원본의 단일 수정 파일·5분 학습·특정 GPU 조건은 범용 요구로 가져오지 않습니다. 프로젝트에 맞는 파일 범위, 시간·횟수 제한, 기존 장치를 사용합니다. 무한 반복 대신 사용자가 맡긴 예산과 종료 조건을 따릅니다. 기존 작업을 지우는 일괄 초기화도 사용하지 않습니다.

출처: [Karpathy AutoResearch README](https://github.com/karpathy/autoresearch/blob/master/README.md), [program.md](https://github.com/karpathy/autoresearch/blob/master/program.md). 위 적용안은 이 프로젝트의 설계 판단이며 원본의 직접 지시가 아닙니다.

## 4. 보완하는 핵심

- **프로젝트 지도:** 목표·데이터·코드·실행 명령·결과의 연결. 근거 위치와 마지막 확인 코드/데이터 버전을 함께 기록합니다.
- **맥락에 맞는 점검:** 분할·전처리 학습 범위·입력/정답 대응·학습/추론 일치·지표 계산을 확인합니다. 연구 가설의 효과는 비교 실험으로 판단합니다.
- **관측과 추론 분리:** 확인한 사실, 의심, 확인 불가, 다음 검사 방법을 구분합니다.
- **전체 파이프라인 개선:** 전처리·피처·모델·loss·optimizer·학습 전략을 변경할 수 있습니다. 파라미터 추천이나 수동 점검 보고서에 머물지 않습니다.
- **실험 기억:** 변경·로그·검증·제출 결과를 연결해 실패를 반복하지 않고 다음 연구에 활용합니다.

## 5. 초기 범위와 완료 조건

사용자가 적용할 때는 프로젝트 구조를 전면 개편하지 않고 기존 명령을 활용합니다. 실험 한 사이클을 완료하면 프로젝트 지침, 근거가 있는 점검 결과, 후보 코드 변경, 실행 결과, 유지·되돌리기·보류 판단이 남아야 합니다. 실제 실행이 불가능하면 누락 정보와 확인하지 못한 항목을 남깁니다.

Docker·원격 작업 관리·OS별 강제 격리·복잡한 자동 복구·독립적인 도구 품질 벤치마크는 초기 필수 범위에서 제외합니다. 실사용 프로젝트의 코드/계산 검사는 필요에 맞게 수행합니다. 제출 점수는 외부 피드백이며 도구의 모든 판단이 옳다는 증명으로 취급하지 않습니다.

현재 개발의 완료 대상은 도구 자체입니다. [v1 계약](cli-and-file-contract.md)에 따라 초기화·점검 근거 기록·실험 비교·제출 점수 연결·보고서 생성이 샘플 파일과 모의 결과로 동작해야 합니다. 실제 ML 학습·제출·현장 적용은 완성 후 사용자가 진행합니다. 대상 ML 프로젝트가 없는 것은 현재 도구 개발의 장애물이 아닙니다.

## 6. 최근 연구의 적용 범위

[2026년 10월 조사와 개선 이슈](research-update-2026-10.md)를 참고합니다. 탐색 계보·실패 기억·평가 조건·후보 선택 기록을 기존 Git+JSON 위에 보완하고, 그래프 DB나 자동 실행 플랫폼은 요구가 입증되기 전 도입하지 않습니다. 논문에서 보고한 성능을 이 도구의 검증 결과로 인용하지 않습니다.

SoL-Pi의 원문 접근 보존과 선택적 조회를 적용해, 필요한 연구 맥락과 근거 줄만 읽도록 했습니다. 자동 문맥 압축·요약 모델 호출은 포함하지 않습니다. 기록 조회의 출력 제한은 연구 중단이나 검증 생략을 뜻하지 않으며 누락·미확인 상태를 명시합니다.
