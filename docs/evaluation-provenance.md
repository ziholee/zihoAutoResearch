# 평가 보호 경로와 비전송 파일 출처 검증

개발 소스의 선택 기능입니다. 공개 v0.3.0에는 포함되지 않습니다. 평가·분할·입력 설정의 변경을 감지하며, 점수의 진실성이나 OS 격리를 보장하지 않습니다. [연구 세션](research-api.md)과 [신뢰 경계](research-trust-boundary.md)의 승인·복구 규칙을 함께 따릅니다.

## 설정

대화형 설정에서 고정할 파일을 명시할 수 있습니다. 다음 명령은 질문과 저장 확인을 거치며 전송 동의는 별도로 받습니다.

```sh
zar research setup --project ./my-ml-project --evaluation-path evaluate.py --provenance-path split.json --provenance-path config.json
```

각 플래그를 반복할 수 있습니다. `--provenance-path`만 지정할 수는 없습니다. 설정은 프로젝트의 선택 필드 `file_contract`로 저장됩니다. 기존 프로젝트에서는 원본과 다른 초안 파일을 만들어 `zar project set --file <draft.json>`으로 같은 필드를 설정할 수도 있습니다.

```json
{
  "file_contract": {
    "version": 1,
    "evaluation_paths": ["evaluate.py"],
    "provenance_paths": ["split.json", "config.json"]
  }
}
```

위 JSON은 추가할 필드 예시이며 전체 project 문서가 아닙니다. `evaluation_paths`는 하나 이상 필요하고 `provenance_paths`는 빈 배열이어도 됩니다. 첫 구현에서 두 목록은 모두 **실험 중 고정할 파일**입니다. 목록끼리 중복하거나 `editable_paths`와 겹치면 거부합니다. 수정할 학습 코드와 고정할 평가 코드를 먼저 분리하세요. 파일 목록은 정확한 프로젝트 상대 경로이며 glob·자동 import 탐색·디렉터리 재귀 탐색은 지원하지 않습니다.

`setup`에 플래그를 주지 않으면 기존 프로젝트의 계약을 유지합니다. `revise`와 `next`도 현재 프로젝트 설정을 사용하며, 이전 세션의 승인을 새 세션으로 복사하지 않습니다. 활성·unknown 작업은 먼저 기존 복구 절차를 따라야 합니다.

## 전송 범위와 검증 범위

`--read`는 기존처럼 모델에 **원문을 전송할 파일**을 정합니다. `file_contract`는 별도로 **로컬에서 해시를 확인할 파일**을 정합니다. 이 기능 때문에 파일 내용이 추가 전송되지는 않습니다. 보호 파일을 사용자가 직접 `--read`에 넣었다면 그 원문은 기존 전송 동의 범위에 포함됩니다.

세션과 실험의 선택 필드 `file_manifest`는 버전, 경로, 분류(`evaluation` 또는 `input`), 바이트 크기와 SHA-256만 보관합니다. 원문은 복사하지 않습니다. 바이너리 파일도 해시할 수 있습니다. 경로·크기·해시와 프로젝트 설정은 모델 맥락이나 기록에 포함될 수 있으므로 익명화 수단으로 보지 마세요.

한 계약은 최대 128개 파일, 파일당 32 MiB, 합계 64 MiB입니다. 64 KiB씩 읽으며 한도를 넘거나 파일이 없거나 일반 파일이 아니면 생략하지 않고 거부합니다. 숨김·탈출·symlink 경로도 거부합니다. 더 큰 데이터는 임의로 제외하거나 조각의 해시를 전체 데이터 해시로 표시하지 말고 검증 범위와 한계를 다시 정해야 합니다.

## 실행과 비교

세션을 만들 때 고정 입력의 manifest를 저장하고 승인·호출·실행·판단 경계에서 현재 파일과 대조합니다. 승인 후 고정 입력이 바뀌면 실행하지 않습니다. 실행 뒤 불일치가 확인되면 성공 점수를 채택하지 않으며 실제 로그·종료 관측은 남깁니다. 원본 파일을 자동 복원하거나 새 해시로 조용히 갱신하지 않습니다.

승인된 학습 코드 변경은 `editable_paths`에서 계속 허용합니다. 비교할 때 후보 코드가 기준 코드와 같을 것을 요구하지 않으며, 별도로 고정한 `file_manifest`가 같아야 합니다. 한쪽 manifest가 없으면 `file_manifest_unknown`, 내용이 다르면 `file_manifest_mismatch`로 비교를 보류합니다. 반복 집계와 기억 선택도 고정 입력 차이를 무시하지 않습니다. 선언된 조건·해시의 일치가 인과 효과를 증명하지는 않습니다.

보호 계약을 사용하는 새 후보는 같은 manifest가 있는 유효한 기준 실험이 필요합니다. 기존 기준에 manifest가 없으면 `--mode baseline`으로 원본 코드를 다시 측정하고 검토·판단 후 선택하세요. 과거 기록을 편집해 새 검증을 수행했던 것처럼 만들지 않습니다.

## 구버전과 복구

계약을 사용하지 않는 기존 프로젝트·세션·실험은 자동 마이그레이션하지 않습니다. manifest가 없는 두 과거 기록은 기존 비교 규칙을 유지하며, 새 파일 검증을 통과했다는 뜻은 아닙니다. 계약을 추가한 프로젝트에서 과거 세션을 그대로 재사용해 검사를 우회하지 않습니다.

실행 여부가 불명확하면 기존 `unknown`을 유지합니다. 실제 프로세스와 로그를 확인하고 새 근거로 기록을 정리한 뒤 재개하세요. `reconcile`이나 판단 저장 도중의 `recover`도 고정 입력 변경을 승인으로 바꾸지 않습니다. 변경된 파일을 새 기준으로 삼으려면 상황을 확인한 뒤 별도 세션에서 시작합니다. 해시·세션 JSON을 직접 고쳐 차단을 해제하지 않습니다.

## 보장 범위와 검증

이 기능은 선택한 파일의 시작·검사 시점·종료 시점 내용을 확인합니다. 실행 중 파일을 바꿨다가 복원하는 동작, 파일 검사 직후의 동시 변경, 악의적 동일 권한 프로세스까지 차단하는 OS 스냅샷이나 샌드박스가 아닙니다. 선택하지 않은 의존 파일은 검증하지 않습니다. Git HEAD·dirty 여부도 전체 파일 내용 증명의 대체물이 아닙니다.

실행 프로그램이 작성한 지표의 진실성은 별도 평가기·데이터 분리로 검증해야 합니다. 여기서는 실제 API 대신 임시 프로젝트·모의 공급자로 보호 경로 중복, 원문 추가 전송 없음, 동일 크기·수정 시각의 내용 변경, 실행 전후 변경, 구버전 및 중단 복구를 검사합니다.

고정 파일끼리 또는 수정 허용 파일과 hardlink·대소문자 별칭으로 같은 실제 파일을 가리키는 경우도 거부합니다. `status`의 `file_provenance.status`는 manifest 존재 여부이며 현재 파일 검증 성공을 뜻하지 않습니다. 현재 파일은 승인·호출·실행·판단·복구 시 검사합니다. 실행 증거에는 `file-manifest.json`과 실행 후 검사 결과인 `file-manifest-result.json`의 해시를 연결합니다.

Windows에서는 경로 조회와 열린 파일 핸들의 `ctime` 의미가 다를 수 있습니다([CPython #157671](https://github.com/python/cpython/issues/157671)). 두 조회 방식 사이에서는 파일 ID·형식·크기·수정 시각을 비교하고, 각 방식의 읽기 전후 비교에는 `ctime`도 유지합니다. 내용 해시·별칭 검사·승인과 복구 규칙은 동일합니다.
