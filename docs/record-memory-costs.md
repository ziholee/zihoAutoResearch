# 대규모 기록 처리와 스냅샷 메모리

2026-10-21 · 합성 기록 10,000개, 완료 세션 0개, 모의 공급자 기준입니다. 실제 API 지연·요금·모델 판단 품질은 검증하지 않습니다.

## 조사 범위와 확인한 원인

[기록 처리 비용](record-processing-costs.md)의 반복 읽기·파싱·문서 검증과 최고 메모리를 다시 측정했습니다. 연구 루프는 각 역할의 호출 전후에 독립적인 기록 스냅샷을 읽어 현재 입력이 승인·계획의 근거와 같은지 확인합니다.

기존 `advance`의 `checked` 변수는 요청 맥락 생성과 세션 저장 후에도 이전 스냅샷을 참조했습니다. 공급자 대기 중에는 전체 스냅샷 하나가 남고, 호출 후 검사 또는 다음 호출 전 검사에서 새 스냅샷과 두 개가 겹쳐 존재했습니다. 10,000개 사전 할당 추적에서 스냅샷 로드 후 현재 할당은 약 63.9MiB에서 128MiB로 증가했습니다. 이는 원인 진단용 관측이며 실제 RSS나 비계측 시간과 같은 수치가 아닙니다.

필요한 요청 맥락을 만들고 세션을 저장한 직후 `checked` 참조를 해제합니다. 요청에 필요한 프로젝트·관측·비교값과 제한된 기록 요약은 유지합니다. 전체 기록 캐시를 추가하거나 파일 읽기·파싱·문서 검증·내용 해시를 건너뛰지 않습니다. 호출 전후 변경 검사, 승인 토큰, 예산, 중단과 재개도 그대로입니다.

## 측정 방법

시간·RSS 대조는 기존 `profile_record_processing.py`를 변경 없이 사용합니다. `control`은 범주 타이머가 꺼져 있지만 기존 벤치마크의 호출 카운터·CLI 출력·저장 세션/토큰 검증을 포함하므로 순수 CLI 시간은 아닙니다. `profiled`는 읽기·파싱·문서 검증·직렬화·해시 등 본문을 배타 분해합니다. 각 쌍의 실행 순서를 번갈아 바꾸고, 준비 1쌍 뒤 3쌍을 측정합니다. 변경 전 전체 실행 후 변경 후 전체 실행 순서이며 각 시점의 환경 변동 한계가 있습니다.

별도 `profile_record_memory.py`는 `tracemalloc`으로 로드·신선도 검사·맥락 생성·공급자 호출 전후의 현재 할당과 누적 최고 할당을 관측합니다. 약한 참조로 살아 있는 `RecordSnapshot`과 포함된 문서 수를 세며 수명을 연장하거나 GC를 강제로 실행하지 않습니다. 단계별 값은 서로 겹치므로 더하지 않으며, 단계 사이 잠깐 생성된 모든 객체의 발생 위치까지 특정하지 않습니다.

할당 진단은 준비 실행 없이 계획·재개 각 1회입니다. 추적 자체가 시간·RSS·할당에 영향을 주므로 이 실행의 시간과 RSS로 성능 개선율을 계산하지 않습니다. 성능 비교는 별도의 control만 사용합니다. 두 도구 모두 입력 생성·복사·재개 준비·부모 검증을 측정에서 제외하며 시간/RSS는 자식 프로세스 범위입니다. 추적 보고서 조립·저장은 추적 종료 후입니다.

```sh
python3.11 scripts/profile_record_processing.py --source /path/to/before --output /tmp/record-cost-before --records 10000 --repeats 3 --label before
python3.11 scripts/profile_record_processing.py --source . --output /tmp/record-cost-after --records 10000 --repeats 3 --label after --compare /tmp/record-cost-before/summary.json
python3.11 scripts/profile_record_memory.py --source /path/to/before --output /tmp/record-memory-before --records 10000 --label before
python3.11 scripts/profile_record_memory.py --source . --output /tmp/record-memory-after --records 10000 --label after --compare /tmp/record-memory-before/summary.json
```

변경 전 소스는 `aad55f5`입니다. 소스·측정 코드·입력 해시를 고정하고, 정식 측정 중에는 다른 테스트·빌드를 병행하지 않습니다. 동일 CLI 의미·역할 순서·최근 기억·호출 예산·승인 토큰과 입력 원문 보존을 검증합니다. 재개는 앞선 2개 역할 응답을 저장하고 세 번째 모의 요청에서 중단한 뒤 새 프로세스에서 나머지 3개 역할을 완료하는 조건입니다. 실제 강제 종료·학습·복구 성능은 이 측정의 범위가 아니며 기존 기능 검사에서 별도로 검증합니다.

## 회귀 검증

약한 참조 수명 검사는 기존 코드에서 다음 로드와 공급자 호출 시 이전 스냅샷이 살아 있어 실패하고, 변경 후 모두 해제돼 통과합니다. 기록 로드 10회(advance 내부 호출 전후 5쌍)는 그대로 유지합니다. 같은 크기·같은 수정 시각의 기록 내용 변경도 호출 후 차단합니다. 기존 추가·삭제·정정·프로젝트 변경·역할 사이 변경 검사, 승인 없는 실행 거부, 중단 후 성공 응답 보존과 재개를 유지합니다.

새 메모리 도구는 약한 참조가 객체를 붙잡지 않는지, 예외 시 계측 깊이가 복원되는지, 다른 스레드가 계측에 섞이지 않는지 검사합니다. 작은 실제 CLI 계획·재개의 의미·입력 보존 및 읽기·파싱·검증 횟수도 확인합니다. 공개 보고서는 수치·버전·해시만 담고 원문·로컬 경로·인증정보를 포함하지 않습니다.

## 정식 시간·RSS 결과

Python 3.11.17 · Darwin-arm64 · 각 조건 3회 중앙값입니다. [변경 전](benchmarks/record-memory-time-before.json)·[변경 후](benchmarks/record-memory-time-after.json) 자료에 비계측 대조와 시간 계측의 모든 표본을 남겼습니다. 아래는 범주 타이머를 끈 control 결과입니다.

| 명령 | 시간 전→후(초) | 최고 RSS 전→후(MiB) | stdout 전→후(바이트) |
|---|---:|---:|---:|
| 계획 | 9.5229 → 9.2679 | 363.06 → 292.56 | 7,588 → 7,589 |
| 재개 | 5.4294 → 6.0487 | 309.09 → 216.11 | 5,991 → 5,989 |

첫 재개 시간이 증가해 코드를 바꾸지 않고 **후→전 순서로 재개 조건 전체를 다시 측정**했습니다. [변경 후 역순 자료](benchmarks/record-memory-resume-after-reverse.json)와 [변경 전 역순 자료](benchmarks/record-memory-resume-before-reverse.json)에서 control 시간은 전→후 **5.4185→5.1311초**, RSS는 **309.11→237.75MiB**였습니다. 첫 실행과 시간 변화의 방향이 다르므로 일괄 속도 향상이나 무회귀를 주장하지 않습니다. 메모리 감소는 두 실행에서 유지됐지만 정확한 RSS 감소량도 실행에 따라 달랐습니다.

모든 control/profiled 표본의 CLI 의미와 원문 보존이 일치했습니다. 총 36개 측정 표본이며 준비 쌍은 제외합니다. stdout의 작은 차이는 시각·호출 시간 등 가변 메타데이터입니다. stderr는 모두 0바이트입니다.

다음은 첫 전후 실행의 **profiled 본문 배타 비용 중앙값**입니다. 계측 오버헤드를 포함하며 control 시간과 직접 합치거나 개선율로 바꾸지 않습니다. 기타는 records_other·digest_other·projection_build·snapshot_identity·worker_other의 항목별 중앙값 합계이므로 개별 표본의 전체 시간 분할과는 구분합니다.

| 명령 | 읽기 전→후 | 파싱 전→후 | 문서 검증 전→후 | 직렬화 전→후 | SHA256 전→후 | 기타 전→후 |
|---|---:|---:|---:|---:|---:|---:|
| 계획 | 1.720 → 1.779 | 2.314 → 1.861 | 1.700 → 1.761 | 2.483 → 2.506 | 0.047 → 0.047 | 1.467 → 1.469 |
| 재개 | 0.958 → 1.118 | 1.272 → 1.106 | 0.947 → 1.065 | 1.482 → 1.622 | 0.028 → 0.030 | 0.767 → 0.799 |

계획은 기록 로드 11회·읽기/파싱/문서 검증 각각 110,000회, 재개는 로드 6회·각각 60,000회로 전후 동일합니다. 기록 요약과 식별자 생성도 각각 1회로 같습니다. 파싱 시간의 변화는 파싱을 생략한 결과가 아니며 GC·할당·파일 캐시·환경 변동 등을 분리해 원인을 확정하지 않았습니다.

## 별도 할당 추적 결과

[변경 전 할당 자료](benchmarks/record-memory-allocation-before.json)·[변경 후 할당 자료](benchmarks/record-memory-allocation-after.json)는 계획·재개 각각 한 번의 진단입니다. 총 4개 표본의 CLI 의미와 입력 보존 검증이 통과했습니다. 아래 수치는 추적된 Python 할당이며, 위 control의 프로세스 RSS와 서로 대체하거나 더하지 않습니다.

| 명령 | 최대 동시 스냅샷 전→후 | 공급자 직전 스냅샷 전→후 | 최고 추적 할당 전→후(MiB) | 공급자 직전 현재 할당 범위 전→후(MiB) |
|---|---:|---:|---:|---:|
| 계획 | 2 → 1 | 1 → 0 | 181.02 → 116.96 | 64.62~64.73 → 0.58~0.68 |
| 재개 | 2 → 1 | 1 → 0 | 180.99 → 116.91 | 64.64~64.68 → 0.57~0.61 |

계획의 로드 완료 시 현재 추적 할당은 기존 최대 128.77MiB에서 변경 후 최대 64.72MiB로 줄었습니다. 약한 참조 기준 두 개의 전체 스냅샷이 겹치는 상태가 사라졌고 공급자 대기 중에는 전체 스냅샷을 보관하지 않습니다. 단일 스냅샷·직렬화 등 필요한 일시 할당은 남아 있어 전체 최고 메모리가 0에 가까워지는 변경은 아닙니다.

새 측정은 단일 로컬 환경과 합성 기록·따뜻한 파일 캐시 기준입니다. 실제 큰 문서·정정 이력·큰 완료 세션이 함께 있는 조건, 다른 OS 및 실제 공급자의 지연·메모리로 일반화하지 않습니다. 추가 파싱 캐시나 파일 검사 생략은 도입하지 않았습니다. 전체 회귀 457개가 통과했으며 실제 API 연결 검증은 보류합니다.
