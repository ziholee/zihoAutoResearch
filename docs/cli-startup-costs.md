# CLI 시작 비용 분해

2026-10-21 · 개발 소스 구현, 공개 v0.3.0에 아직 포함되지 않았습니다.

[로컬 루프 비용 분해](local-loop-costs.md)의 시작 시간에는 Python 시작·import·계측 준비가 섞여 있었습니다. 이번에는 새 프로세스의 시작부터 import, 명령 초기화, 실행, 종료까지 나누고 동일 명령을 계측 없이 실행한 대조 결과를 함께 남깁니다. 실제 API 연결은 수행하지 않습니다.

## 확인된 원인과 변경

기존 `cli.parse`는 모든 명령을 등록하면서 `research.add_arguments`를 import했습니다. 이 때문에 일반 도움말과 프로젝트 상태 조회에도 연구 실행부와 HTTP·SSL 의존성을 불러왔습니다. `-X importtime` 진단에서 이 경로를 확인하고, 같은 명령의 비계측 전후 실행으로 영향을 확인합니다.

연구 명령 정의만 `research_arguments.py`로 옮기고 CLI는 이 가벼운 모듈을 사용합니다. 인자·도움말·필수 승인 토큰 정의는 동일하며 `research.add_arguments`도 기존처럼 사용할 수 있습니다. 실제 연구 명령을 실행할 때에는 기존 `research` 실행부가 로드됩니다. 연구 명령 실행 자체에서 모든 import 비용이 사라진다고 주장하지 않습니다.

승인·검토·실행·저장·중단·재개 코드는 변경하지 않습니다. 데몬, 프로세스 간 캐시, 검사 생략 또는 새 런타임 의존성을 추가하지 않습니다.

## 재현과 측정 구간

Python 3.11 이상으로 이전 소스와 개선 소스를 준비하고, 같은 현재 측정 스크립트에서 비교합니다. `--source`의 `zar`를 임시 폴더로 복사하여 실행하므로 설치된 패키지와 섞이지 않습니다. 출력은 새 파일이어야 합니다.

```sh
python scripts/benchmark_cli_startup.py --source /path/to/before --output /tmp/startup-before.json --repeats 7
python scripts/benchmark_cli_startup.py --source . --output /tmp/startup-after.json --repeats 7
# 두 소스에 대해 위 명령에 --bytecode disabled를 추가하면 바이트코드 없는 조건도 비교합니다.
```

기본 `--bytecode warm`은 각 명령의 비계측 실행을 한 번 수행해 바이트코드를 준비하며 이 준비 시간은 제외합니다. `disabled`는 바이트코드 읽기·쓰기가 없는 새 복사본을 사용합니다. 반복마다 명령 순서와 계측/비계측 순서를 바꿉니다. 두 소스 간 순서는 전→후이므로 장시간에 걸친 시스템 상태 변화는 통제하지 못합니다.

항목은 Python 진입 전, 계측 준비, CLI import, 명령 초기화 중 import, 나머지 명령 초기화, 본문 import, 나머지 본문, 종료 잔여입니다. 각 시행의 합은 해당 계측 총시간과 같습니다. 개별 항목 중앙값의 합은 총시간 중앙값과 다를 수 있습니다. 준비·출력 대조는 시간 밖에서 수행하고, 프로세스 종료와 계측 결과 쓰기는 종료 잔여에 남깁니다.

`research_status_missing`은 존재하지 않는 세션을 조회하여 실제 연구 실행부 import와 예상 오류 코드 3을 확인합니다. 유효한 세션의 조회 성능 측정이 아닙니다. 다른 세 명령은 종료 코드 0이며, 모든 조건에서 계측·비계측 stdout/stderr/종료 코드가 일치해야 합니다.

## 관측 결과

macOS arm64, Python 3.11.17에서 다른 회귀·빌드·설치 검사를 끝낸 뒤 직렬 측정했습니다. 기준은 `7f1da4d`입니다. 아래는 새 프로세스 **비계측 대조 7회의 중앙값**입니다.

| 명령 | 캐시 준비 조건: 코드 변경 전 → 후 | 캐시 미사용 조건: 코드 변경 전 → 후 |
|---|---:|---:|
| `--help` | 57.570 → 41.641ms | 76.083 → 54.095ms |
| `status --json` | 58.306 → 42.233ms | 73.818 → 57.988ms |
| `research --help` | 58.874 → 41.351ms | 74.482 → 54.623ms |
| 없는 세션의 `research status` | 58.042 → 53.694ms | 75.599 → 73.872ms |

바이트코드 준비 조건의 도움말·일반 상태 조회에서는 약 16~18ms가 줄었습니다. 연구 상태 조회의 작은 차이는 실행부 import가 제거된 결과가 아니므로 연구 실행 속도 향상으로 주장하지 않습니다.

같은 조건에서 계측된 `status`의 구간별 중앙값은 다음과 같습니다.

| 구간 | 전 | 후 |
|---|---:|---:|
| Python 진입 전 | 13.295ms | 13.068ms |
| 계측 준비 | 6.024ms | 5.984ms |
| CLI import | 15.973ms | 15.832ms |
| 명령 초기화 중 import | 12.813ms | 0.175ms |
| 나머지 명령 초기화 | 3.587ms | 3.456ms |
| 본문 import | 0.006ms | 0.005ms |
| 나머지 본문 | 0.680ms | 0.641ms |
| 종료 잔여 | 5.886ms | 4.438ms |

없는 세션의 연구 상태 조회에서는 명령 초기화 중 import가 12.664→0.177ms로 줄지만, 본문 import가 0.003→12.034ms로 이동합니다. 필요한 실행부는 그대로 로드한다는 근거입니다.

바이트코드 준비 조건에서 명령별 계측−비계측 차이의 중앙값은 변경 전 1.902~3.621ms, 변경 후 1.570~3.342ms였습니다. 준비 구간의 약 6ms를 이 차이에 다시 더하지 않습니다. 계측 실행기의 import 순서가 달라 단순 차감으로 순수 계측 비용을 산출할 수 없습니다.

개별 반복·계측 차이·중첩 import 진단·소스 및 측정 스크립트 해시는 원자료에 있습니다: [준비 전](benchmarks/cli-startup-before-warm.json), [준비 후](benchmarks/cli-startup-after-warm.json), [미사용 전](benchmarks/cli-startup-before-disabled.json), [미사용 후](benchmarks/cli-startup-after-disabled.json). 여기서 전/후는 코드 변경 전후이며, “준비”는 바이트코드 캐시 준비 조건입니다.

## 해석과 검증

계측 결과는 원인을 진단하는 자료이며 제품 속도 판단은 비계측 대조를 기준으로 합니다. 계측과 비계측의 차이에는 실행기·후킹·import 순서 차이와 시스템 잡음도 포함됩니다. 각 반복은 새 프로세스이지만 OS 파일 캐시가 초기화된 콜드 부팅 측정은 아닙니다. 한 환경의 짧은 명령 측정을 전체 실험 루프·실제 공급자 지연·토큰 비용으로 확대하지 않습니다.

계측 실행기는 `runpy`, `json`, `pathlib` 등을 CLI보다 먼저 불러옵니다. 따라서 계측의 `cli_import`를 비계측 CLI의 순수 import 비용이라고 읽으면 안 됩니다. 시작 항목에는 부모 프로세스의 실행 준비와 최소 `time` import도 포함됩니다. 명령 초기화는 `cli.parse`에서 import를 뺀 시간으로, argparse의 명령 등록뿐 아니라 인자 해석·도움말 출력도 포함합니다. 최상위 import 진단은 해당 구간 안에 포함되며 합계에 다시 더하지 않습니다.

명령 파싱에서 공급자 실행부가 로드되지 않는 검사를 수정 전 실패·수정 후 통과로 확인합니다. 기존 전체 회귀 및 설치 패키지 검사로 승인·검토·모의 학습·중단·재개·unknown 보존을 대조합니다. 도움말 및 출력·종료 코드가 달라지는 최적화는 허용하지 않습니다. 실제 모델의 판단 품질·인증·호환성은 후속 검증입니다.

전체 회귀 412개와 새 계측 대상 검사 4개, wheel 격리 설치·sdist의 모의 실험 및 실제 CLI 장애 복구 검증이 통과했습니다. 독립 리뷰에서 이전 명령 정의와 새 정의의 AST가 동일함을 확인했습니다. `mandela` 관점에서 고정 명령의 시간·출력 대조는 재현 가능한 관측이지만, 실제 사용자 편익이나 모델 판단 품질의 증거는 아닙니다.
