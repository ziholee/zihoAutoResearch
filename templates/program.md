# 프로젝트 연구 지침

v1에서는 zar init이 이 양식을 .autoresearch/program.md에 생성합니다. 기존 사용자 지침을 덮어쓰지 않습니다. 스킬이 아래 서술 부분을 채우며, CLI는 이 Markdown에서 설정이나 상태를 추출하지 않습니다.

## 먼저 읽을 원본

- 설정·지표·예산·명령·현재 선택: 같은 폴더의 project.json
- 점검 근거: reviews/의 JSON
- 실험·실행·판단: experiments/의 JSON
- 제출 결과: submissions/의 JSON

이 정보의 값은 여기에 별도로 복사하지 않습니다. 보고서는 JSON에서 생성한 읽기용 자료입니다. 필수 설정이 비어 있으면 코드·문서에서 먼저 확인하고, 임의 추정이 필요한 작업은 보류합니다.

## 프로젝트 해석 — 스킬이 작성

- 문제/대회 설명과 출처:
- 예측 단위·시점과 정답 의미:
- 코드 흐름과 근거 위치: 전처리 → 학습 → 검증 → 추론
- 데이터의 시간·그룹 구조와 주의할 점:
- 현재 코드/데이터에서 확인하지 못한 사항:
- 위 해석의 마지막 확인 코드·데이터 식별자:

## 수행 절차

1. project.json과 기존 프로젝트 지침을 읽고 맡겨진 범위와 남은 예산을 확인한다.
2. 문제에 해당하는 분할·전처리·정답 대응·학습·평가를 점검하고 근거를 reviews JSON으로 남긴다. 코드가 바뀌면 관련 판정을 재확인한다.
3. 비교를 무효로 만드는 문제를 먼저 고친다. 점수가 낮아져도 오류 코드로 돌아가지 않는다. 분할·지표·데이터가 바뀌면 새 비교 구간에서 기준을 확보한다.
4. 가설·코드/설정·명령·기준을 정하고 planned 실험을 만든다. 실제 사용 중 실행은 기존 에이전트 도구로 수행하며 CLI 기록 명령이 학습을 시작하지 않는다.
5. 실행 상태·점수·로그를 experiment update로 기록한다. 실패 점수는 null이며 과거 로그를 새 실행의 결과로 사용하지 않는다.
6. 같은 조건에서 비교한 뒤 판단과 근거를 decide로 남긴다. 이 명령은 코드·Git을 수정하지 않는다. 코드의 유지/복구는 별도 작업이며 자신의 변경만 다룬다.
7. keep 후 현재 선택을 바꾸려면 project.json을 갱신한다. hold이면 기존 선택을 유지하고 후보 코드·산출물을 식별해 보존한다.
8. 제출 파일 생성과 실제 제출은 구분한다. 이 CLI는 실제 제출을 수행하지 않는다. 제출 결과는 파일 해시·실험·출처와 연결한다.
9. 맡겨진 한도 안에서 반복하고 종료 시 현재 코드와 기록상 선택이 일치하는지 확인한다.

## 판정과 재개

- 확인된 문제 / 의심 / 확인 범위 내 통과 / 확인 불가 / 해당 없음을 구분한다.
- 수치 차이만으로 개선을 확정하지 않고 프로젝트에 맞는 변동·복잡도 근거를 확인한다.
- 종료 시 실행 여부를 확인한다. 알 수 없으면 unknown과 확인 방법을 남기고, 재개 시 확인 전 같은 작업을 반복 실행하지 않는다.
- 매 실험마다 재확인하지 않는다. 필수 정보나 맡겨지지 않은 작업이 필요할 때 해당 단계만 보류한다.
- 다음 행동·현재 선택 ID는 project.json에 기록한다. 서술형 해석과 구조화된 상태를 혼동하지 않는다.
